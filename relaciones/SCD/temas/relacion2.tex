\begin{ejercicio}[37: Coordinación de Secuencias de Procesos con Semáforos]
Tres procesos ejecutan indefinidamente las siguientes secuencias:
\begin{lstlisting}[language=C++]
process P1: while true do begin a; b; c end
process P2: while true do begin d; e; f end
process P3: while true do begin g; h; i end
\end{lstlisting}
Resolver independientemente mediante semáforos los siguientes requisitos. En (a)--(c), la condición se refiere a la misma ronda $k$ de ejecución de cada proceso, numerada desde 1; evitar que señales de rondas futuras satisfagan esperas de rondas anteriores. Si una solución exige sincronización de fin de ronda, explicitarla:
\begin{enumerate}[label=(\alph*)]
    \item $P_2$ ejecuta $e_k$ solamente después de que haya terminado $a_k$ o $g_k$ (basta una de las dos).
    \item $P_2$ ejecuta $e_k$ solamente después de que hayan terminado $a_k$ y $g_k$.
    \item $P_2$ ejecuta $e_k$ y $P_3$ ejecuta $h_k$ solamente después de que $P_1$ haya terminado $b_k$; ambas autorizaciones son independientes.
    \item A lo sumo dos de las operaciones $b$, $f$ y $h$ pueden estar ejecutándose simultáneamente.
\end{enumerate}
\end{ejercicio}

\begin{solucion}
\textbf{Apartado (a): OR Lógico ($a_k$ o $g_k$ habilita $e_k$ en la ronda $k$):}\\
Para evitar que si ambos terminan se generen dos fichas en el semáforo (lo que satisfaría espuriamente la ronda $k+1$), se utiliza una variable protegida \texttt{notificado} por ronda y una barrera de fin de ronda:
\begin{lstlisting}[language=C++]
sem_t sem_e = 0;        // Autoriza a P2 a ejecutar e
sem_t mutex = 1;        // Protege la variable notificado
sem_t fin_ronda_1 = 0, fin_ronda_3 = 0; // Sincronizacion de fin de ronda
bool notificado = false;

// Proceso P1:
while (true) {
    a();
    sem_wait(&mutex);
    if (!notificado) { notificado = true; sem_post(&sem_e); }
    sem_post(&mutex);
    b(); c();
    sem_wait(&fin_ronda_1); // Espera a que P2 complete la ronda
}

// Proceso P2:
while (true) {
    d();
    sem_wait(&sem_e);   // Espera autorizacion de a o de g
    e();
    f();
    sem_wait(&mutex);
    notificado = false; // Reset para la siguiente ronda k+1
    sem_post(&mutex);
    sem_post(&fin_ronda_1);
    sem_post(&fin_ronda_3);
}

// Proceso P3:
while (true) {
    g();
    sem_wait(&mutex);
    if (!notificado) { notificado = true; sem_post(&sem_e); }
    sem_post(&mutex);
    h(); i();
    sem_wait(&fin_ronda_3);
}
\end{lstlisting}

\textbf{Apartado (b): AND Lógico ($a_k$ y $g_k$ deben terminar antes de $e_k$):}\\
Se requieren dos semáforos binarios independientes inicializados a 0, y $P_2$ ejecuta sendos \texttt{wait}:
\begin{lstlisting}[language=C++]
sem_t sem_a = 0, sem_g = 0;
sem_t fin_ronda_1 = 0, fin_ronda_3 = 0;

// P1: a(); sem_post(&sem_a); b(); c(); sem_wait(&fin_ronda_1);
// P3: g(); sem_post(&sem_g); h(); i(); sem_wait(&fin_ronda_3);
// P2: d(); sem_wait(&sem_a); sem_wait(&sem_g); e(); f();
//     sem_post(&fin_ronda_1); sem_post(&fin_ronda_3);
\end{lstlisting}

\textbf{Apartado (c): Bifurcación independiente tras $b_k$ (habilita $e_k$ y $h_k$):}\\
$P_1$ notifica a través de dos semáforos distintos y espera a que ambos procesos completen su uso antes de pasar a la ronda $k+1$:
\begin{lstlisting}[language=C++]
sem_t sem_p2 = 0, sem_p3 = 0;
sem_t fin_p2 = 0, fin_p3 = 0;

// P1: a(); b(); sem_post(&sem_p2); sem_post(&sem_p3); c(); sem_wait(&fin_p2); sem_wait(&fin_p3);
// P2: d(); sem_wait(&sem_p2); e(); f(); sem_post(&fin_p2);
// P3: g(); sem_wait(&sem_p3); h(); i(); sem_post(&fin_p3);
\end{lstlisting}

\textbf{Apartado (d): A lo sumo 2 operaciones de $\{b, f, h\}$ simultáneas:}\\
Este es el patrón canónico de exclusión mutua generalizada ($N$-aforo). Se define un \textbf{semáforo contador inicializado a 2}:
\begin{lstlisting}[language=C++]
sem_t aforo_bfh = 2; // Invariante: 0 <= aforo_bfh <= 2

// En P1: a(); sem_wait(&aforo_bfh); b(); sem_post(&aforo_bfh); c();
// En P2: d(); e(); sem_wait(&aforo_bfh); f(); sem_post(&aforo_bfh);
// En P3: g(); sem_wait(&aforo_bfh); h(); sem_post(&aforo_bfh); i();
\end{lstlisting}
\textbf{Invariante de seguridad:} En todo instante se cumple:
\[
(\text{en\_b} + \text{en\_f} + \text{en\_h}) + \text{valor}(aforo\_bfh) = 2 \implies \text{en\_b} + \text{en\_f} + \text{en\_h} \le 2.
\]
\end{solucion}

\begin{ejercicio}[38: Productor-Consumidor sobre Variable Simple]
Dos procesos comparten la variable global $x$. Las constantes $n$ y $c$ son inmutables; $m$ y $d$ son locales:
\begin{lstlisting}[language=C++]
process P1: while true do begin m := 2*x - n; imprimir(m); end
process P2: while true do begin d := leer_teclado(); x := d - 5*c; end
\end{lstlisting}
Diseñar dos protocolos mediante semáforos:
\begin{enumerate}[label=(\alph*)]
    \item Consumir exactamente una vez todos los valores producidos, en orden y sin sobrescrituras.
    \item Consumir exactamente los valores de orden impar ($1, 3, 5, \dots$), descartando los de orden par, sin duplicaciones ni lecturas inconsistentes.
\end{enumerate}
\end{ejercicio}

\begin{solucion}
\textbf{Apartado (a): Consumo 1 a 1 de todos los valores:}\\
Se utilizan dos semáforos binarios que forman un cerrojo alternante (\emph{ping-pong}):
\begin{lstlisting}[language=C++]
sem_t libre = 1;     // P2 puede producir
sem_t ocupado = 0;   // P1 puede consumir

// Proceso P1 (Consumidor):
while (true) {
    sem_wait(&ocupado);
    m = 2 * x - n;
    sem_post(&libre);
    imprimir(m);
}

// Proceso P2 (Productor):
while (true) {
    d = leer_teclado();
    sem_wait(&libre);
    x = d - 5 * c;
    sem_post(&ocupado);
}
\end{lstlisting}
$P_2$ se bloquea si produce un valor antes de que $P_1$ lo consuma. Se garantiza que cada valor producido se consume exactamente una vez en orden.

\textbf{Apartado (b): Consumo exclusivo de los valores de orden impar ($1, 3, 5, \dots$):}\\
$P_2$ cuenta las producciones mediante una variable local. Si la producción es par, no avisa a $P_1$; si es impar, avisa y espera lectura:
\begin{lstlisting}[language=C++]
sem_t libre = 1;
sem_t ocupado = 0;

// Proceso P1 (Consumidor):
while (true) {
    sem_wait(&ocupado); // Solo despierta en valores impares
    m = 2 * x - n;
    sem_post(&libre);
    imprimir(m);
}

// Proceso P2 (Productor):
int orden = 0;
while (true) {
    d = leer_teclado();
    orden++;
    if (orden % 2 != 0) {
        // Valor impar: debe ser consumido obligatoriamente por P1
        sem_wait(&libre);
        x = d - 5 * c;
        sem_post(&ocupado);
    } else {
        // Valor par: se descarta sin que P1 lo consuma
        sem_wait(&libre);
        x = d - 5 * c;
        sem_post(&libre); // Se libera inmediatamente para la siguiente produccion
    }
}
\end{lstlisting}
\end{solucion}

\begin{ejercicio}[39: El Aseo Compartido con Semáforos POSIX]
Un aseo admite simultáneamente o bien una mujer o bien hasta cinco hombres; nunca ambos a la vez. Resolver con semáforos POSIX no nombrados:
\begin{enumerate}[label=(\alph*)]
    \item Prioridad estricta de hombres: si hay hombres esperando, ninguna mujer nueva puede entrar, incluso si el aforo masculino está completo.
    \item Prioridad estricta de mujeres: si hay mujeres esperando, ningún hombre nuevo puede entrar.
\end{enumerate}
\end{ejercicio}

\begin{solucion}
Se modela la variante (a) (Prioridad a Hombres). Se mantienen contadores protegidos para hombres dentro ($H$), hombres esperando ($H_{esp}$), mujeres dentro ($M$) y mujeres esperando ($M_{esp}$):
\begin{lstlisting}[language=C++]
sem_t mutex = 1;
sem_t sem_hombres = 0;
sem_t sem_mujeres = 0;
int H = 0, H_esp = 0;
int M = 0, M_esp = 0;

void entrar_hombre() {
    sem_wait(&mutex);
    H_esp++;
    // Puede entrar si no hay mujeres dentro y hay menos de 5 hombres
    if (M == 0 && H < 5) {
        H_esp--;
        H++;
        sem_post(&sem_hombres);
    }
    sem_post(&mutex);
    sem_wait(&sem_hombres);
}

void salir_hombre() {
    sem_wait(&mutex);
    H--;
    // Si quedan hombres esperando, entra el siguiente hombre
    if (H_esp > 0 && H < 5) {
        H_esp--;
        H++;
        sem_post(&sem_hombres);
    } else if (H == 0 && H_esp == 0 && M_esp > 0) {
        // Si no quedan hombres, pasa una mujer
        M_esp--;
        M = 1;
        sem_post(&sem_mujeres);
    }
    sem_post(&mutex);
}

void entrar_mujer() {
    sem_wait(&mutex);
    // Prioridad a hombres: solo entra si H == 0, M == 0 y NO hay hombres esperando
    if (H == 0 && M == 0 && H_esp == 0) {
        M = 1;
        sem_post(&sem_mujeres);
    } else {
        M_esp++;
    }
    sem_post(&mutex);
    sem_wait(&sem_mujeres);
}

void salir_mujer() {
    sem_wait(&mutex);
    M = 0;
    // Tienen prioridad los hombres que esperan
    if (H_esp > 0) {
        int a_despertar = std::min(H_esp, 5);
        H_esp -= a_despertar;
        H += a_despertar;
        for (int k = 0; k < a_despertar; k++) sem_post(&sem_hombres);
    } else if (M_esp > 0) {
        M_esp--;
        M = 1;
        sem_post(&sem_mujeres);
    }
    sem_post(&mutex);
}
\end{lstlisting}
\textbf{Discusión sobre Inanición:} La prioridad estricta causa \textbf{inanición de mujeres} si el flujo de llegada de hombres es continuo ($H_{esp} > 0$). Los semáforos POSIX no garantizan política FIFO en el desbloqueo, por lo que dentro de la misma clase el planificador del kernel puede elegir arbitrariamente.
\end{solucion}

\begin{ejercicio}[40: Reentrancia frente a Exclusión Mutua en Monitores]
Un monitor garantiza exclusión mutua al ejecutar sus procedimientos. Explicar qué significa que un procedimiento sea reentrante, por qué exclusión mutua y reentrancia no son equivalentes y en qué situaciones es necesario exigir reentrancia. Distinguir la semántica de señales Hoare (SU) y Mesa (SC).
\end{ejercicio}

\begin{solucion}
\begin{itemize}[leftmargin=*]
    \item \textbf{Definición de Reentrancia:} Un código es reentrante si puede ser interrumpido a mitad de su ejecución por otro hilo (o por una llamada recursiva/señal) y reanudado posteriormente sin que su estado lógico resulte alterado. Para ello, \textbf{no debe modificar variables estáticas o globales no protegidas} y debe almacenar su estado local exclusivamente en la pila (\emph{stack}) del hilo invocador.
    \item \textbf{No equivalencia con Exclusión Mutua:} La exclusión mutua restringe el acceso a un solo hilo a la vez, pero no previene que si un procedimiento realiza una llamada recursiva sobre sí mismo o cede el monitor en un \texttt{wait}, el estado local sea sobreescrito si reside en memoria estática.
    \item \textbf{Situaciones donde se exige reentrancia:}
    \begin{enumerate}
        \item Cuando un hilo en un monitor invoca \texttt{c.wait()} o \texttt{c.signal()}: el hilo cede el monitor y otro hilo puede entrar al mismo procedimiento. Si las variables locales estuvieran en variables globales del monitor, el nuevo hilo las destruiría.
        \item Invocaciones cruzadas o recursivas entre procedimientos del monitor.
    \end{enumerate}
    \item \textbf{Diferencia entre SU y SC:}
    \begin{itemize}
        \item \textbf{SU (Hoare):} El señalador pasa a la cola urgente y el despertado entra de inmediato. La condición lógica se garantiza intacta tras \texttt{wait} (basta \texttt{if (!cond) wait()}).
        \item \textbf{SC (Mesa):} El señalador retiene el monitor y el despertado va a la cola de entrada. La condición puede ser invalidada por otro hilo antes de que el despertado tome el control, haciendo \textbf{obligatorio el bucle} \texttt{while (!cond) wait()}.
    \end{itemize}
\end{itemize}
\end{solucion}

\begin{ejercicio}[41: Dos Tipos de Recursos Indistinguibles y Prevención de Interbloqueo]
Un sistema dispone de $N_1 > 0$ unidades de recurso tipo 1 y $N_2 > 0$ de tipo 2. Demostrar cómo surge interbloqueo y diseñar un monitor que lo evite.
\end{ejercicio}

\begin{solucion}
\textbf{1. Escenario de Interbloqueo:}\\
Si el proceso $A$ pide primero 1 unidad de $N_1$ y luego 1 de $N_2$, mientras que el proceso $B$ pide primero 1 de $N_2$ y luego 1 de $N_1$, se puede llegar al estado donde $N_1$ y $N_2$ quedan agotados: $A$ retiene $N_1$ y espera $N_2$, y $B$ retiene $N_2$ y espera $N_1$. Cumple las 4 condiciones de Coffman $\implies$ \textbf{Interbloqueo circular}.

\textbf{2. Diseño del Monitor con Asignación Atómica (Todo o Nada):}
\begin{lstlisting}[language=C++]
class MonitorRecursos {
private:
    std::mutex cerrojo;
    std::condition_variable cola;
    int libres1, libres2;

public:
    MonitorRecursos(int n1, int n2) : libres1(n1), libres2(n2) {}

    void adquirir(int p1, int p2) {
        std::unique_lock<std::mutex> lock(cerrojo);
        // Condicion atomica: solo pasa si se pueden satisfacer AMBOS recursos
        while (libres1 < p1 || libres2 < p2) {
            cola.wait(lock);
        }
        libres1 -= p1;
        libres2 -= p2;
    }

    void liberar(int l1, int l2) {
        std::unique_lock<std::mutex> lock(cerrojo);
        libres1 += l1;
        libres2 += l2;
        cola.notify_all(); // Despertar a los solicitantes bloqueados
    }
};
\end{lstlisting}
Al concederse los recursos de forma atómica (\emph{all-or-nothing}), se destruye la condición de Coffman de \textbf{retención y espera}, impidiendo formalmente el interbloqueo.
\end{solucion}

\begin{ejercicio}[42: Lectores-Escritores con Monitores]
Resolver el problema de lectores y escritores mediante monitores con prioridad a escritores y con política equitativa sin inanición.
\end{ejercicio}

\begin{solucion}
\textbf{Variante con Prioridad a Escritores:} Si hay algún escritor esperando o escribiendo, los nuevos lectores deben bloquearse:
\begin{lstlisting}[language=C++]
class LectoresEscritoresPrioridadEscritores {
private:
    std::mutex cerrojo;
    std::condition_variable cola_lectores, cola_escritores;
    int num_lectores = 0;
    bool escribiendo = false;
    int escritores_esperando = 0;

public:
    void iniciar_lectura() {
        std::unique_lock<std::mutex> lock(cerrojo);
        while (escribiendo || escritores_esperando > 0) {
            cola_lectores.wait(lock);
        }
        num_lectores++;
    }

    void fin_lectura() {
        std::unique_lock<std::mutex> lock(cerrojo);
        num_lectores--;
        if (num_lectores == 0 && escritores_esperando > 0) {
            cola_escritores.notify_one();
        }
    }

    void iniciar_escritura() {
        std::unique_lock<std::mutex> lock(cerrojo);
        escritores_esperando++;
        while (escribiendo || num_lectores > 0) {
            cola_escritores.wait(lock);
        }
        escritores_esperando--;
        escribiendo = true;
    }

    void fin_escritura() {
        std::unique_lock<std::mutex> lock(cerrojo);
        escribiendo = false;
        if (escritores_esperando > 0) {
            cola_escritores.notify_one();
        } else {
            cola_lectores.notify_all();
        }
    }
};
\end{lstlisting}
\end{solucion}

\begin{ejercicio}[43: Puente de un Solo Carril con Cupo Máximo]
Vehículos del norte y del sur cruzan un puente de un solo carril.
\begin{enumerate}[label=(\alph*)]
    \item Monitor básico y discusión de inanición.
    \item Modificación para conceder turnos de hasta diez entradas consecutivas cuando hay espera opuesta.
\end{enumerate}
\end{ejercicio}

\begin{solucion}
\textbf{Apartado (a):} En la política básica (entran del norte si no hay coches del sur cruzando), si llega un flujo ininterrumpido de coches del norte, los coches del sur sufrirán \textbf{inanición indefinida}.

\textbf{Apartado (b): Monitor con Cupo de 10 Coches y Alternancia Justa:}
\begin{lstlisting}[language=C++]
class MonitorPuenteCupo {
private:
    std::mutex cerrojo;
    std::condition_variable cola_norte, cola_sur;
    int coches_cruzando = 0;
    int sentido_actual = 0; // 0: vacio, 1: Norte, 2: Sur
    int esperando_norte = 0, esperando_sur = 0;
    int cupo_actual = 0;    // Contador de coches en la ronda actual (max 10)

public:
    void entrarNorte() {
        std::unique_lock<std::mutex> lock(cerrojo);
        esperando_norte++;
        while ((sentido_actual == 2 && coches_cruzando > 0) ||
               (sentido_actual == 1 && cupo_actual >= 10 && esperando_sur > 0)) {
            cola_norte.wait(lock);
        }
        esperando_norte--;
        sentido_actual = 1;
        coches_cruzando++;
        cupo_actual++;
    }

    void salirNorte() {
        std::unique_lock<std::mutex> lock(cerrojo);
        coches_cruzando--;
        if (coches_cruzando == 0) {
            if (cupo_actual >= 10 || esperando_norte == 0) {
                // Cambio de sentido hacia el Sur
                cupo_actual = 0;
                sentido_actual = (esperando_sur > 0) ? 2 : 0;
                cola_sur.notify_all();
            } else {
                cola_norte.notify_all();
            }
        }
    }
    // Funciones analogas para entrarSur() y salirSur() invirtiendo los roles
};
\end{lstlisting}
\end{solucion}

\begin{ejercicio}[44: La Olla de los Salvajes y el Cocinero]
Olla de capacidad $M > 0$ raciones y $N > 0$ comensales. El primer salvaje que encuentra la olla vacía despierta al cocinero; el resto espera sin generar nuevas llamadas. Diseñar el monitor con semántica SU.
\end{ejercicio}

\begin{solucion}
\begin{lstlisting}[language=C++]
Monitor Olla {
    int raciones = M;      // Capacidad inicial llena
    cond cola_salvajes;
    cond cola_cocinero;
    bool aviso_enviado = false;

    procedure servir() {
        // En semantica SU, basta un if porque la senal reactiva de inmediato
        if (raciones == 0) {
            if (!aviso_enviado) {
                aviso_enviado = true;
                cola_cocinero.signal(); // Despierta al cocinero (pasa a cola urgente)
            }
            cola_salvajes.wait();
        }
        raciones = raciones - 1;
        if (raciones > 0) {
            cola_salvajes.signal(); // Efecto cascada: avisa al siguiente salvaje
        }
    }

    procedure esperarPeticion() {
        if (!aviso_enviado) {
            cola_cocinero.wait();
        }
    }

    procedure reponer() {
        raciones = M;
        aviso_enviado = false;
        cola_salvajes.signal(); // Despierta al primer salvaje en espera
    }
}
\end{lstlisting}
\textbf{Invariante:} $0 \le raciones \le M$. Si $raciones == 0$, ningún salvaje puede completar \texttt{servir()} antes de que el cocinero reponga.
\end{solucion}

\begin{ejercicio}[45: Cuenta Bancaria Compartida con Saldo No Negativo]
Saldo inicial $S_0 \ge 0$. Procedimientos \texttt{ingresar(c)} y \texttt{retirar(c)} ($c > 0$). Resolver bajo políticas:
\begin{enumerate}[label=(\alph*)]
    \item Concesión en cuanto hay saldo suficiente (con colas normales y con colas de prioridad por importe solicitado).
    \item Orden estricto de llegada (FIFO).
\end{enumerate}
\end{ejercicio}

\begin{solucion}
\textbf{Apartado (a.2): Cola de prioridad por importe solicitado ($c$ mínimo primero):}\\
Bajo semántica SU, se utiliza una variable condición con prioridad ordenada por el importe $c$:
\begin{lstlisting}[language=C++]
Monitor CuentaAhorrosPrioridadImporte {
    int saldo = S0;
    cond_p cola_retiradas; // Cola de condicion con prioridad por c

    procedure ingresar(int c) {
        saldo = saldo + c;
        // Despertar mientras haya fondos para el que pide menos
        while (!cola_retiradas.empty() && cola_retiradas.min_p() <= saldo) {
            cola_retiradas.signal();
        }
    }

    procedure retirar(int c) {
        if (saldo < c) {
            cola_retiradas.wait(c); // Se suspende con prioridad = c
        }
        saldo = saldo - c;
        if (!cola_retiradas.empty() && cola_retiradas.min_p() <= saldo) {
            cola_retiradas.signal();
        }
    }
}
\end{lstlisting}

\textbf{Apartado (b): Orden estricto de llegada (FIFO con Ticket):}\\
\begin{lstlisting}[language=C++]
Monitor CuentaFIFO {
    int saldo = S0;
    int ticket_turno = 0;
    int ticket_siguiente = 0;
    cond cola_espera;

    procedure ingresar(int c) {
        saldo = saldo + c;
        cola_espera.signal_all(); // Notifica para que el del turno revalide
    }

    procedure retirar(int c) {
        int mi_ticket = ticket_siguiente++;
        while (mi_ticket != ticket_turno || saldo < c) {
            cola_espera.wait();
        }
        saldo = saldo - c;
        ticket_turno++;
        cola_espera.signal_all();
    }
}
\end{lstlisting}
\end{solucion}

\begin{ejercicio}[46: Recurso Indivisible con Prioridades y Envejecimiento]
$n \ge 1$ procesos comparten un recurso $R$. Cada $P_i$ tiene prioridad fija $i$ (índice menor = mayor prioridad). Diseñar monitor y política de envejecimiento para evitar inanición.
\end{ejercicio}

\begin{solucion}
\begin{lstlisting}[language=C++]
Monitor RecursoPrioridad {
    bool ocupado = false;
    cond_p cola_espera; // Cola ordenada por prioridad efectiva

    procedure solicitar(int id, int prioridad_base) {
        if (ocupado) {
            cola_espera.wait(prioridad_base);
        }
        ocupado = true;
    }

    procedure liberar() {
        ocupado = false;
        if (!cola_espera.empty()) {
            cola_espera.signal(); // Despierta al de menor indice numerico
        }
    }
}
\end{lstlisting}
\textbf{Envejecimiento (\emph{Aging}):} Si llegan continuamente procesos de prioridad alta, los de prioridad baja sufren inanición. Para impedirlo, cada vez que un proceso completa el recurso, se decrementa en 1 unidad la prioridad efectiva de todos los procesos que continúen esperando en la cola (\texttt{prioridad\_efectiva = max(1, prioridad\_base - esperas)}), garantizando que cualquier petición alcanzará eventualmente la máxima prioridad (ausencia de inanición).
\end{solucion}

\begin{ejercicio}[47: Barrera Cíclica de Dos Participantes (Semáforos Puros)]
Implementar una barrera cíclica reutilizable para dos hilos utilizando exclusivamente semáforos y contadores. Evitar que una señal de la ronda $k$ libere erróneamente a un hilo de la ronda $k+1$.
\end{ejercicio}

\begin{solucion}
Se utiliza el esquema clásico del \textbf{Doble Torniquete} (\emph{Two-Turnstile}):
\begin{lstlisting}[language=C++]
sem_t mutex = 1;
sem_t torniquete1 = 0;
sem_t torniquete2 = 1; // Segundo torniquete cerrado para la fase de salida
int contador = 0;

void llegar() {
    // FASE 1: Llegada y bloqueo
    sem_wait(&mutex);
    contador++;
    if (contador == 2) {
        sem_wait(&torniquete2); // Bloquea la salida de la fase previa
        sem_post(&torniquete1); // Abre el paso del primer torniquete
    }
    sem_post(&mutex);

    sem_wait(&torniquete1); // Espera de fase
    sem_post(&torniquete1); // Cascada

    // FASE 2: Salida y preparacion para la siguiente ronda
    sem_wait(&mutex);
    contador--;
    if (contador == 0) {
        sem_wait(&torniquete1); // Cierra el primer torniquete
        sem_post(&torniquete2); // Abre el segundo torniquete
    }
    sem_post(&mutex);

    sem_wait(&torniquete2);
    sem_post(&torniquete2);
}
\end{lstlisting}
El segundo torniquete impide que el primer hilo que supere la barrera complete la siguiente ronda e interactúe con el contador antes de que el segundo hilo haya salido de la ronda actual.
\end{solucion}

\begin{ejercicio}[48: Los Cinco Filósofos Comensales con Monitor]
Cinco filósofos comparten 5 tenedores.
\begin{enumerate}[label=(\alph*)]
    \item Adquisición individual en monitor y corrección de la liberación.
    \item Ejecución con interbloqueo.
    \item Prevención mediante limitación de aforo a 4 filósofos.
\end{enumerate}
\end{ejercicio}

\begin{solucion}
\textbf{Apartado (a) y (b): Interbloqueo Circular:}\\
Si cada filósofo $i$ toma primero su tenedor izquierdo $T_i$, todos los 5 filósofos retienen un tenedor y esperan el derecho $T_{(i+1)\%5}$. Hay un ciclo de espera cerrada $\implies$ \textbf{Interbloqueo}.

\textbf{Apartado (c): Solución con Aforo de 4 Filósofos:}
\begin{lstlisting}[language=C++]
class MonitorFilosofosAforo {
private:
    std::mutex cerrojo;
    std::condition_variable cola_aforo;
    std::condition_variable cola_tenedores[5];
    bool tenedor_libre[5] = {true, true, true, true, true};
    int comiendo_o_esperando = 0;

public:
    void entrar_a_comer(int i) {
        std::unique_lock<std::mutex> lock(cerrojo);
        // Aforo maximo 4: garantiza que al menos un filosofo podra tomar ambos tenedores
        while (comiendo_o_esperando >= 4) {
            cola_aforo.wait(lock);
        }
        comiendo_o_esperando++;

        while (!tenedor_libre[i]) cola_tenedores[i].wait(lock);
        tenedor_libre[i] = false;

        while (!tenedor_libre[(i + 1) % 5]) cola_tenedores[(i + 1) % 5].wait(lock);
        tenedor_libre[(i + 1) % 5] = false;
    }

    void salir_de_comer(int i) {
        std::unique_lock<std::mutex> lock(cerrojo);
        tenedor_libre[i] = true;
        tenedor_libre[(i + 1) % 5] = true;
        cola_tenedores[i].notify_one();
        cola_tenedores[(i + 1) % 5].notify_one();

        comiendo_o_esperando--;
        cola_aforo.notify_one();
    }
};
\end{lstlisting}
Por el Principio del Palomar, con 4 filósofos y 5 tenedores, al menos uno tendrá disponibles sus dos tenedores contiguos, garantizando \textbf{ausencia absoluta de interbloqueo}.
\end{solucion}

\begin{ejercicio}[49: Canal Acotado con Cierre y Terminación Limpia]
Canal de capacidad $K \ge 1$ con $p \ge 2$ productores y $q \ge 2$ consumidores. Implementar con semáforos un mecanismo de cierre sin marcadores centinela que desbloquee limpiamente a todos los consumidores al vaciarse.
\end{ejercicio}

\begin{solucion}
\begin{lstlisting}[language=C++]
sem_t mutex = 1;
sem_t libres = K;
sem_t ocupados = 0;
int productores_activos = p;
bool canal_cerrado = false;
int elementos_en_buffer = 0;

void enviar(T elem) {
    sem_wait(&libres);
    sem_wait(&mutex);
    buffer.push(elem);
    elementos_en_buffer++;
    sem_post(&mutex);
    sem_post(&ocupados);
}

void terminar_productor() {
    sem_wait(&mutex);
    productores_activos--;
    if (productores_activos == 0) {
        canal_cerrado = true;
        // Despertar a posibles consumidores bloqueados
        for (int i = 0; i < q; i++) sem_post(&ocupados);
    }
    sem_post(&mutex);
}

bool recibir(T &elem) {
    sem_wait(&ocupados);
    sem_wait(&mutex);
    if (elementos_en_buffer == 0 && canal_cerrado) {
        // Cascada para liberar a otros consumidores terminados
        sem_post(&ocupados);
        sem_post(&mutex);
        return false; // Senal de fin de canal
    }
    elem = buffer.pop();
    elementos_en_buffer--;
    sem_post(&mutex);
    sem_post(&libres);
    return true;
}
\end{lstlisting}
\end{solucion}

\begin{ejercicio}[50: Asignación Multidimensional de Recursos Todo o Nada]
Tres clases de recursos $(N_A, N_B, N_C)$. Diseñar monitor con reserva atómica, comparar FIFO frente a primera satisfacible y política de envejecimiento.
\end{ejercicio}

\begin{solucion}
\begin{lstlisting}[language=C++]
class MonitorMultirrecurso {
private:
    std::mutex cerrojo;
    std::condition_variable cola;
    int dispA, dispB, dispC;
    int ticket_turno = 0;
    int ticket_siguiente = 0;

public:
    void adquirir_fifo(int a, int b, int c) {
        std::unique_lock<std::mutex> lock(cerrojo);
        int mi_ticket = ticket_siguiente++;
        while (mi_ticket != ticket_turno || dispA < a || dispB < b || dispC < c) {
            cola.wait(lock);
        }
        dispA -= a; dispB -= b; dispC -= c;
        ticket_turno++;
        cola.notify_all();
    }

    void liberar(int a, int b, int c) {
        std::unique_lock<std::mutex> lock(cerrojo);
        dispA += a; dispB += b; dispC += c;
        cola.notify_all();
    }
};
\end{lstlisting}
\textbf{Comparativa de Políticas de Admisión:}
\begin{itemize}
    \item \textbf{Primera satisfacible:} Maximiza el uso del hardware al no bloquear peticiones pequeñas si hay una grande esperando, pero produce \textbf{inanición de procesos con solicitudes grandes}.
    \item \textbf{FIFO estricto:} Garantiza vivacidad y equidad absoluta a costa de reducir el rendimiento global si la cabeza de la cola pide más de lo disponible.
\end{itemize}
\end{solucion}

\begin{ejercicio}[51: Barrera Reutilizable con Bajas Dinámicas y Plazo Vencido]
Barrera para $N \ge 3$ hilos con generaciones numeradas, soporte de bajas y semántica de barrera rota (\emph{broken barrier}).
\end{ejercicio}

\begin{solucion}
Si vence el plazo de espera (\emph{timeout}) de uno de los hilos, se produce la ruptura de la barrera: todos los hilos que esperan en esa misma generación son despertados lanzando una excepción \texttt{BrokenBarrierException}:
\begin{lstlisting}[language=C++]
class BarreraGeneracional {
private:
    std::mutex cerrojo;
    std::condition_variable cola;
    int participantes_activos;
    int esperando = 0;
    int generacion = 0;
    bool rota = false;

public:
    BarreraGeneracional(int n) : participantes_activos(n) {}

    void darse_de_baja() {
        std::unique_lock<std::mutex> lock(cerrojo);
        participantes_activos--;
        if (esperando == participantes_activos) {
            generacion++;
            esperando = 0;
            cola.notify_all();
        }
    }

    void sincronizar(int timeout_ms) {
        std::unique_lock<std::mutex> lock(cerrojo);
        int gen_local = generacion;
        if (rota) throw std::runtime_error("Barrera Rota");

        esperando++;
        if (esperando == participantes_activos) {
            esperando = 0;
            generacion++;
            cola.notify_all();
            return;
        }

        auto status = cola.wait_for(lock, std::chrono::milliseconds(timeout_ms),
            [&] { return generacion != gen_local || rota; });

        if (!status) {
            rota = true;
            cola.notify_all();
            throw std::runtime_error("Timeout: Barrera Rota");
        }
        if (rota) throw std::runtime_error("Barrera Rota por otro hilo");
    }
};
\end{lstlisting}
\end{solucion}

\begin{ejercicio}[53: Transferencias Concurrentes entre Dos Servicios Independientes]
Servicios $A$ y $B$ con saldos no negativos. No se permite monitor global ni retener un monitor esperando en otro.
\end{ejercicio}

\begin{solucion}
\textbf{1. Prevención de Interbloqueo con Orden Parcial de Cierres:}\\
Si una transferencia $A \to B$ adquiere primero el cerrojo de $A$ y luego el de $B$, mientras una transferencia $B \to A$ adquiere primero $B$ y luego $A$, surge interbloqueo.
\textbf{Solución:} Establecer una regla de orden global en memoria (ej. por dirección o identificador alfabético $id_A < id_B$):
\begin{lstlisting}[language=C++]
void transferir(Servicio &origen, Servicio &destino, int cantidad) {
    Servicio &primero = (origen.id < destino.id) ? origen : destino;
    Servicio &segundo = (origen.id < destino.id) ? destino : origen;

    std::unique_lock<std::mutex> lk1(primero.cerrojo);
    std::unique_lock<std::mutex> lk2(segundo.cerrojo);

    if (origen.saldo >= cantidad) {
        origen.saldo -= cantidad;
        destino.saldo += cantidad;
    }
}
\end{lstlisting}
\textbf{Invariante Global de Conservación:} En todo estado se verifica:
\[
\text{Saldo}(A) + \text{Saldo}(B) = \text{Saldo Inicial}(A) + \text{Saldo Inicial}(B)
\]
\textbf{2. Tolerancia a Fallos:} En sistemas distribuidos con caída de nodos, la transferencia debe dividirse en dos fases (Protocolo Two-Phase Commit - 2PC) con un identificador unívoco de transacción y un registro persistente (\emph{write-ahead log}) para deshacer cargos parciales si el nodo receptor colapsa.
\end{solucion}

\begin{ejercicio}[54: Propiedades de Corrección: Seguridad, Vivacidad y Condiciones de Dijkstra]
Considerar las cuatro exigencias habituales del problema de la exclusión mutua: exclusión mutua, progreso o ausencia de interbloqueo, ausencia de inanición y espera acotada (equidad). Clasificar cada una como propiedad de seguridad o de vivacidad, precisando las hipótesis necesarias sobre la planificación. Explicar mediante ejemplos por qué garantizar exclusión mutua y ausencia de interbloqueo no implica necesariamente ausencia de inanición. ¿Qué se puede afirmar de un algoritmo que únicamente satisface las cuatro condiciones de Dijkstra estudiadas en clase? Explicitar qué formulación de dichas condiciones se utiliza.
\end{ejercicio}

\begin{solucion}
\textbf{1. Clasificación Formal de las Propiedades (Seguridad frente a Vivacidad):}\\
Conforme a la caracterización axiomática de Alpern y Schneider (1985) y Leslie Lamport:
\begin{itemize}[leftmargin=*]
    \item \textbf{Propiedad de Seguridad (\emph{Safety}):} Estipula que \emph{«nada malo ocurrirá jamás»} durante la ejecución ($\Box P$). Puede refutarse en un prefijo finito de traza: si en algún estado alcanzable se viola la condición, dicha violación es definitiva e irremediable.
    \item \textbf{Propiedad de Vivacidad (\emph{Liveness}):} Estipula que \emph{«algo bueno terminará ocurriendo eventualmente»} ($\lozenge P$). No puede refutarse en ningún prefijo finito, pues siempre cabe la posibilidad de que el evento deseado ocurra en el futuro; exige considerar trazas de longitud infinita.
\end{itemize}

Desglose formal de las cuatro exigencias:
\begin{center}
\resizebox{\linewidth}{!}{%
\begin{tabular}{p{3.8cm}cp{5.2cm}p{4.2cm}}
\toprule
\textbf{Propiedad} & \textbf{Clase} & \textbf{Definición Formal} & \textbf{Hipótesis de Planificación} \\ \midrule
\textbf{Exclusión Mutua} & \textbf{Seguridad} & En todo estado $s$: $N_{SC}(s) \le 1$. Nunca coexisten dos procesos en SC. & Ninguna (invariante de estados global). \\ \addlinespace[4pt]
\textbf{Progreso (Ausencia de Interbloqueo)} & \textbf{Vivacidad} & Si $N_{SC} = 0$ y $\exists i$ en protocolo de entrada, $\lozenge (\exists j : j \text{ entra a SC})$. & Planificación mínimamente justa (\emph{weak fairness} en CPU). \\ \addlinespace[4pt]
\textbf{Ausencia de Inanición} & \textbf{Vivacidad} & Si el proceso $P_i$ solicita entrar, $\lozenge (P_i \text{ entra a SC})$. & Planificación justa (\emph{fairness}) individual. \\ \addlinespace[4pt]
\textbf{Espera Acotada (Equidad)} & \textbf{Seguridad} & $\exists K \in \mathbb{N}$ tal que ningún rival entra $> K$ veces mientras $P_i$ espera. & Planificación débilmente justa y tiempo acotado en SC. \\
\bottomrule
\end{tabular}%
}
\end{center}

\vspace{6pt}
\noindent\textbf{2. Demostración de que Exclusión Mutua + Progreso $\not\Rightarrow$ Ausencia de Inanición:}\\
La ausencia de interbloqueo es una propiedad de progreso \textbf{colectivo} (el conjunto de procesos avanza globalmente), mientras que la ausencia de inanición es una propiedad de progreso \textbf{individual} (cada proceso concreto avanza).

\textbf{Ejemplo constructivo:} Consideremos 3 procesos $P_0, P_1, P_2$. Un recurso es arbitrado mediante una variable \texttt{turno} $\in \{0, 1\}$. 
\begin{itemize}[leftmargin=*]
    \item $P_2$ solicita entrar en el instante $t_0$ y queda esperando en un bucle \texttt{while (recurso\_ocupado) skip;}.
    \item El planificador intercala alternativamente las solicitudes de $P_0$ y $P_1$: $P_0$ entra a la SC, sale y cede el turno a $P_1$; a continuación $P_1$ entra a la SC, sale y cede el turno a $P_0$, repitiendo indefinidamente la secuencia:
    \[
    \sigma = \langle P_0^{SC} \to P_0^{salida} \to P_1^{SC} \to P_1^{salida} \to P_0^{SC} \to P_0^{salida} \dots \rangle
    \]
    \item En todo instante se cumple la \textbf{exclusión mutua} ($N_{SC} \le 1$).
    \item Se satisface el \textbf{progreso global} (no hay interbloqueo, pues en cada intervalo finito algún proceso accede a la SC).
    \item Sin embargo, el proceso $P_2$ es postergado eternamente y sufre \textbf{inanición estricta}.
\end{itemize}

\vspace{6pt}
\noindent\textbf{3. Formulación y Alcance de las Cuatro Condiciones de Dijkstra (1965):}\\
Se utiliza la formulación canónica publicada por Edsger W. Dijkstra en 1965:
\begin{enumerate}[leftmargin=*,noitemsep]
    \item \textbf{C1 (Exclusión Mutua):} En ningún instante de tiempo puede haber más de un proceso dentro de su sección crítica.
    \item \textbf{C2 (Independencia del Hardware):} No se hacen suposiciones sobre el número de procesadores ni sobre la velocidad relativa de ejecución de los procesos.
    \item \textbf{C3 (Progreso):} Ningún proceso detenido o ejecutando en su sección no crítica (SNC) puede impedir que otros procesos accedan a la sección crítica. Si ningún proceso está en la SC y hay procesos solicitando entrada, la elección no puede posponerse indefinidamente.
    \item \textbf{C4 (Ausencia de Inanición):} Ningún proceso debe esperar indefinidamente para acceder a su sección crítica si manifiesta su interés.
\end{enumerate}

\textbf{Qué se puede afirmar de un algoritmo que únicamente satisface las 4 condiciones:}\\
Un algoritmo que cumpla estrictamente las 4 condiciones de Dijkstra es un algoritmo concurrentemente correcto en seguridad y vivacidad individual. Sin embargo:
\begin{itemize}[leftmargin=*]
    \item \textbf{No garantiza FIFO determinista:} No asegura que los procesos sean atendidos en el orden cronológico estricto de sus solicitudes.
    \item \textbf{No garantiza una cota fija uniforme de espera independiente de $N$:} En algoritmos como el propio de Dijkstra (1965), un proceso puede ser adelantado múltiples veces de forma dependiente de las carreras entre rivales antes de entrar.
    \item \textbf{No tolera fallos por parada en SC:} Si un proceso colapsa dentro de su SC, el sistema completo se detiene.
\end{itemize}
\end{solucion}

\begin{ejercicio}[55: Dos Indicadores sin Variable de Turno (Cuarto Intento de Dijkstra)]
Sean dos procesos con las variables compartidas \texttt{b[0]} y \texttt{b[1]}, inicialmente falsas, y el siguiente protocolo, ejecutado por $P(i)$ ($j=1-i$):
\begin{lstlisting}[language=C++]
b[i] := true;
while b[j] do
    b[i] := false;
    while b[j] do skip;
    b[i] := true;
endwhile;
<seccion critica>;
b[i] := false;
\end{lstlisting}
Analizar por separado: (a) exclusión mutua; (b) ausencia de interbloqueo; (c) ausencia de inanición. Si alguna propiedad no se satisface, construir un escenario concreto. Comparar el papel de la variable de turno en este algoritmo y en el de Peterson para dos procesos.
\end{ejercicio}

\begin{solucion}
\textbf{Apartado (a): Exclusión Mutua (SÍ se garantiza):}\\
Demostraremos por contradicción que nunca pueden coexistir ambos procesos en la SC:
\begin{itemize}[leftmargin=*]
    \item Para que $P_0$ se encuentre en la SC, ha debido salir del bucle \texttt{while b[1]} evaluando $b[1] == \text{false}$. Previamente fijó $b[0] := \text{true}$, y no ejecuta $b[0] := \text{false}$ hasta abandonar la SC. Por tanto, mientras $P_0 \in \text{SC}$, $b[0] = \text{true}$.
    \item Para que $P_1$ esté simultáneamente en la SC, debió evaluar su guarda \texttt{while b[0]} como \texttt{false}.
    \item Si $P_0 \in \text{SC}$, $b[0] = \text{true}$. La única forma en que $P_1$ pudo ver $b[0] == \text{false}$ es que $P_0$ se encontrara temporalmente en su fase de cortesía ($b[0] := \text{false}$, línea 3).
    \item No obstante, si $P_0$ estaba en la línea 3, para que $P_1$ continuase hacia la SC debió tener $b[1] = \text{true}$. Esto hace que $P_0$ quede atrapado en su bucle interno \texttt{while b[1] do skip;} (línea 4) mientras $P_1$ permanezca activo, impidiendo que $P_0$ reasigne $b[0]:=\text{true}$ y alcance la SC.
    \item Es lógicamente imposible que ambos procesos superen a la vez sus respectivos bucles externos. Por tanto:
    \[
    N_{SC} \le 1 \quad \text{(Exclusión mutua demostrada)}
    \]
\end{itemize}

\textbf{Apartado (b): Ausencia de Interbloqueo (NO se garantiza: Livelock Dinámico):}\\
El algoritmo no sufre interbloqueo estático (las instrucciones no se bloquean permanentemente en cerrojos mudos), pero adolece de un \textbf{bloqueo activo o livelock} simétrico en paso síncrono (\emph{lock-step}):

\begin{center}
\resizebox{\linewidth}{!}{%
\begin{tabular}{cllccc}
\toprule
\textbf{Paso} & \textbf{Acción $P_0$} & \textbf{Acción $P_1$} & $b[0]$ & $b[1]$ & \textbf{Estado del Sistema} \\ \midrule
1 & $b[0] := \text{true}$ & $b[1] := \text{true}$ & true & true & Ambos manifiestan intención. \\
2 & Evalúa: \texttt{while b[1]} (V) & Evalúa: \texttt{while b[0]} (V) & true & true & Ambos entran al bucle externo. \\
3 & $b[0] := \text{false}$ (cede) & $b[1] := \text{false}$ (cede) & false & false & Cortesía simultánea. \\
4 & Evalúa interno: \texttt{b[1]} (F) & Evalúa interno: \texttt{b[0]} (F) & false & false & Ambos salen del bucle interno. \\
5 & $b[0] := \text{true}$ & $b[1] := \text{true}$ & true & true & Ambos reafirman intención. \\
6 & \multicolumn{5}{c}{\textit{El sistema regresa exactamente al Paso 2. Ciclo infinito sin entrada a SC.}} \\
\bottomrule
\end{tabular}%
}
\end{center}
Si el planificador ejecuta ambos procesos a ritmos idénticos, ninguno accede jamás a la SC. Se viola la propiedad de progreso.

\textbf{Apartado (c): Ausencia de Inanición (NO se garantiza):}\\
Como consecuencia directa del livelock anterior, ambos procesos sufren inanición simultánea. Asimismo, en una ejecución asimétrica donde $P_0$ sea sistemáticamente más lento que $P_1$, $P_0$ puede quedar bloqueado en su bucle interno mientras $P_1$ aprovecha para entrar y salir repetidas veces.

\textbf{Comparación con el papel de la variable de turno en Peterson:}\\
\begin{itemize}[leftmargin=*]
    \item \textbf{En este algoritmo:} Las decisiones se sustentan exclusivamente en indicadores simétricos $b[0]$ y $b[1]$. Ante una contienda concurrente, ambos observan un estado idéntico y adoptan la misma conducta de cortesía ("pase usted primero"), generando la oscilación infinita.
    \item \textbf{En el Algoritmo de Peterson:} Se incorpora la variable compartida \texttt{turno}. Cuando ambos procesos compiten y asignan \texttt{quiere[i] := true}, ambos ejecutan inmediatamente \texttt{turno := 1-i}. La escritura atómica de \texttt{turno} en el hardware resuelve el conflicto de forma asimétrica e instantánea: el último proceso en escribir sobrescribe la variable y asume el rol de víctima. La condición de espera \texttt{quiere[j] and turno == j} resulta cierta para uno solo de los procesos, forzando a que el otro entre de inmediato a la SC.
\end{itemize}
\end{solucion}

\begin{ejercicio}[56: El Algoritmo de Hyman y la Violación de Exclusión Mutua]
Se comparte \texttt{c[0]=c[1]=1} y \texttt{turno=1}. Cada proceso $P(i)$, con $j=1-i$, ejecuta:
\begin{lstlisting}[language=C++]
c[i] := 0;
while turno != i do
    while c[j] = 0 do skip;
    turno := i;
endwhile;
<seccion critica>;
c[i] := 1;
\end{lstlisting}
Determinar si el algoritmo garantiza exclusión mutua. Si no la garantiza, proporcionar una intercalación de instrucciones que lleve simultáneamente a ambos procesos a sus secciones críticas. Identificar exactamente la decisión de diseño que permite el fallo.
\end{ejercicio}

\begin{solucion}
\textbf{1. Determinación de la Propiedad:}\\
\textbf{EL ALGORITMO DE HYMAN NO GARANTIZA LA EXCLUSIÓN MUTUA.} A pesar de haber sido publicado en 1966 en \emph{Communications of the ACM} como una simplificación del algoritmo de Dekker, contiene una sutil condición de carrera que invalida la seguridad.

\textbf{2. Intercalación de Instrucciones (Contraejemplo Detallado):}\\
Estado inicial: \texttt{c[0] = 1}, \texttt{c[1] = 1}, \texttt{turno = 1}.
\begin{center}
\resizebox{\linewidth}{!}{%
\begin{tabular}{cllcccp{4.5cm}}
\toprule
\textbf{Paso} & \textbf{Proceso} & \textbf{Instrucción Ejecutada} & $c[0]$ & $c[1]$ & \textbf{turno} & \textbf{Efecto y Comentario} \\ \midrule
1 & $P_0$ & \texttt{c[0] := 0;} & 0 & 1 & 1 & $P_0$ manifiesta interés. \\
2 & $P_0$ & Evalúa \texttt{while turno != 0} & 0 & 1 & 1 & Condición \textbf{True} ($1 \ne 0$). Entra. \\
3 & $P_0$ & Evalúa \texttt{while c[1] == 0} & 0 & 1 & 1 & Condición \textbf{False} ($c[1]=1$). No espera. \\
4 & --- & \multicolumn{4}{c}{\textit{Planificador suspende a $P_0$ antes de asignar \texttt{turno := 0}}} & Interrupción de contexto crítica. \\
5 & $P_1$ & \texttt{c[1] := 0;} & 0 & 0 & 1 & $P_1$ manifiesta interés. \\
6 & $P_1$ & Evalúa \texttt{while turno != 1} & 0 & 0 & 1 & Condición \textbf{False} ($\text{turno}=1$). \\
7 & $P_1$ & \textbf{Entra a Sección Crítica} & 0 & 0 & 1 & $P_1$ omite el bucle y accede. \\
8 & $P_0$ & \texttt{turno := 0;} & 0 & 0 & 0 & $P_0$ se reanuda y cambia turno. \\
9 & $P_0$ & Reevalúa \texttt{while turno != 0} & 0 & 0 & 0 & Condición \textbf{False} ($\text{turno}=0$). \\
10 & $P_0$ & \textbf{Entra a Sección Crítica} & 0 & 0 & 0 & $P_0$ sale del bucle y accede. \\ \midrule
\multicolumn{7}{c}{\textbf{ESTADO FINAL: $P_0 \in \text{SC} \ \land \ P_1 \in \text{SC} \implies N_{SC} = 2$. VIOLACIÓN DE EXCLUSIÓN MUTUA.}} \\
\bottomrule
\end{tabular}%
}
\end{center}

\textbf{3. Decisión de Diseño Errónea (Causa Raíz del Fallo):}\\
El defecto radica en una vulnerabilidad de tipo \textbf{TOCTOU (Time-of-Check to Time-of-Use)} unida a una apropiación no sincronizada del turno:
\begin{enumerate}[leftmargin=*]
    \item \textbf{Desacoplamiento entre comprobación y apropiación:} $P_0$ verifica que $P_1$ no está en el bucle (\texttt{c[1] == 1}), pero antes de ejecutar la asignación \texttt{turno := 0}, $P_1$ puede activarse.
    \item \textbf{Confianza ciega en el turno previo:} $P_1$ ingresa a la SC sin comprobar el estado de $c[0]$, amparándose exclusivamente en que $\text{turno} == 1$.
    \item \textbf{Apropiación incondicional del turno:} Cuando $P_0$ despierta, ejecuta $\text{turno} := 0$ sin revalidar si $P_1$ ha iniciado la SC mientras estaba suspendido, saliendo del bucle sin encontrar ningún obstáculo.
\end{enumerate}
\end{solucion}

\begin{ejercicio}[57: Algoritmo de Peterson para Dos Procesos: Demostración y Memoria Débil]
Sean \texttt{quiere[0]=quiere[1]=false} y \texttt{turno} compartido. Cada $P(i)$ ejecuta:
\begin{lstlisting}[language=C++]
quiere[i] := true;
turno := 1-i;
while quiere[1-i] and turno = 1-i do skip;
<seccion critica>;
quiere[i] := false;
\end{lstlisting}
(a) Demostrar la exclusión mutua. (b) Argumentar el progreso y la ausencia de inanición, indicando las hipótesis de planificación. (c) Investigar qué sucede si se intercambia el orden de las dos primeras asignaciones. (d) Explicar por qué la corrección en un modelo secuencialmente consistente no autoriza a usar sin más variables ordinarias en un programa real con memoria débil.
\end{ejercicio}

\begin{solucion}
\textbf{Apartado (a): Demostración Rigurosa de Exclusión Mutua:}\\
Demostraremos por contradicción lógica:
\begin{itemize}[leftmargin=*]
    \item Supongamos que en el instante $t$, ambos procesos $P_0$ y $P_1$ se encuentran simultáneamente en la SC.
    \item Para que $P_0$ esté en SC, debió evaluar su guarda de espera como falsa:
    \[
    \neg (\texttt{quiere[1]} \land \texttt{turno} = 1) \iff (\neg \texttt{quiere[1]} \lor \texttt{turno} \ne 1)
    \]
    \item Para que $P_1$ esté en SC, análogamente debió cumplirse:
    \[
    \neg (\texttt{quiere[0]} \land \texttt{turno} = 0) \iff (\neg \texttt{quiere[0]} \lor \texttt{turno} \ne 0)
    \]
    \item Puesto que ambos están en SC y no han ejecutado el protocolo de salida, necesariamente $\texttt{quiere[0]} = \text{true}$ y $\texttt{quiere[1]} = \text{true}$.
    \item En consecuencia, para que ambas expresiones sean verdaderas debe cumplirse forzosamente:
    \[
    (\texttt{turno} \ne 1 \implies \texttt{turno} = 0) \quad \land \quad (\texttt{turno} \ne 0 \implies \texttt{turno} = 1)
    \]
    \item La variable \texttt{turno} es una celda atómica en memoria que sólo puede almacenar un valor escalar en cada instante. Como la asignación a \texttt{turno} es la última instrucción antes del bucle en ambos procesos, una de las dos asignaciones debió completarse en último lugar en el bus de memoria:
    \begin{itemize}[leftmargin=*]
        \item Si $P_0$ escribió en último lugar, $\texttt{turno} = 1$. Entonces $P_0$ no pudo observar $\texttt{turno} = 0$, quedando bloqueado en el bucle.
        \item Si $P_1$ escribió en último lugar, $\texttt{turno} = 0$. Entonces $P_1$ no pudo observar $\texttt{turno} = 1$, quedando bloqueado en el bucle.
    \end{itemize}
    \item Se llega a una contradicción formal insalvable. Por tanto, $N_{SC} \le 1$.
\end{itemize}

\textbf{Apartado (b): Progreso y Ausencia de Inanición:}\\
\begin{itemize}[leftmargin=*]
    \item \textbf{Progreso:} Si ningún proceso está en la SC y ambos compiten a la vez, \texttt{turno} adopta el valor 0 o 1. El proceso para el cual $\texttt{turno} \ne 1-i$ (aquel que escribió primero) supera el bucle y accede. Si solo un proceso desea entrar, $\texttt{quiere[1-i]} = \text{false}$, accediendo sin retardo alguno.
    \item \textbf{Ausencia de Inanición:} Asumiendo \textbf{planificación débilmente justa} (los procesos activos reciben ciclos de CPU y terminan su SC en tiempo finito), cuando el proceso rival $P_j$ abandona la SC ejecuta $\texttt{quiere[j]} := \text{false}$. En ese instante, la guarda de $P_i$ se vuelve inmediatamente falsa y $P_i$ entra. Si $P_j$ intentara reingresar con rapidez, ejecutará $\texttt{turno} := i$, cediéndole la prioridad a $P_i$. La cota de espera es estricta: \textbf{a lo sumo 1 entrada del proceso rival}.
\end{itemize}

\textbf{Apartado (c): Intercambio de las dos primeras asignaciones:}\\
Si el protocolo se altera a:
\begin{lstlisting}[language=C++]
turno := 1-i;
quiere[i] := true;
while quiere[1-i] and turno = 1-i do skip;
\end{lstlisting}
\textbf{Se destruye la Exclusión Mutua.} Traza de contraejemplo:
\begin{enumerate}[leftmargin=*,noitemsep]
    \item $P_0$ ejecuta $\texttt{turno} := 1$.
    \item Planificador conmuta a $P_1$.
    \item $P_1$ ejecuta $\texttt{turno} := 0$.
    \item $P_1$ ejecuta $\texttt{quiere[1]} := \text{true}$.
    \item $P_1$ evalúa el bucle: $\texttt{quiere[0]}$ sigue en \texttt{false}, luego $P_1$ entra a la SC.
    \item Planificador conmuta a $P_0$.
    \item $P_0$ ejecuta $\texttt{quiere[0]} := \text{true}$.
    \item $P_0$ evalúa el bucle: $\texttt{turno} = 0$. Como $\texttt{turno} == 0 \ne 1$, la guarda es falsa.
    \item $P_0$ accede a la SC \textbf{simultáneamente con $P_1$}. Violación de exclusión mutua.
\end{enumerate}

\textbf{Apartado (d): Consistencia Secuencial frente a Memoria Débil (\emph{Weak Memory}):}\\
La demostración matemática asume el modelo de \textbf{Consistencia Secuencial de Lamport (1979)}, donde toda lectura y escritura se ejecuta en estricto orden de código y es visible de inmediato para todos los hilos.
\begin{itemize}[leftmargin=*]
    \item En procesadores modernos (x86, ARM, RISC-V) y compiladores optimizadores (GCC/Clang), las escrituras se colocan en \emph{Store Buffers} locales para evitar latencias de memoria. Esto permite la reordenación \textbf{Store-Load}: la lectura de \texttt{quiere[1-i]} puede adelantarse antes de que la escritura de \texttt{quiere[i]} se haya hecho visible en la caché compartida del otro núcleo.
    \item Ambos hilos pueden leer simultáneamente $\texttt{quiere[1-i]} == \text{false}$, accediendo a la vez a la SC en hardware real.
    \item Por ello, en programas reales es obligatorio declarar las variables con tipos atómicos (\texttt{std::atomic<bool>}) bajo ordenación secuencialmente consistente (\texttt{memory\_order\_seq\_cst}) o insertar barreras completas de memoria (\texttt{mfence} en x86, \texttt{dmb} en ARM).
\end{itemize}
\end{solucion}

\begin{ejercicio}[58: Sincronización Hardware para N Procesos con Instrucción Atómica Swap]
Se dispone de \texttt{swap(x,y)}, que intercambia atómicamente los valores booleanos de $x$ e $y$. Diseñar protocolos de entrada y salida para $N \ge 2$ procesos mediante una variable compartida \texttt{ocupado}, inicialmente falsa, y una variable booleana local por proceso. Demostrar la exclusión mutua y discutir el progreso, la inanición y el coste de espera ocupada. ¿Basta la atomicidad de \texttt{swap} para asegurar equidad? Justificar.
\end{ejercicio}

\begin{solucion}
\textbf{1. Diseño de los Protocolos de Entrada y Salida:}\\
Variables compartidas y privadas:
\begin{lstlisting}[language=C++]
// Variable compartida global:
bool ocupado = false;

// Protocolo de Entrada para el proceso Pi:
bool mi_llave = true; // Variable local privada
do {
    swap(ocupado, mi_llave);
} while (mi_llave == true);

// < Seccion Critica >

// Protocolo de Salida para el proceso Pi:
ocupado = false;
\end{lstlisting}

\textbf{2. Demostración de la Exclusión Mutua:}\\
\begin{itemize}[leftmargin=*]
    \item \textbf{Invariante de conservación del testigo:} En todo instante se cumple:
    \[
    \text{Valor}(\texttt{ocupado}) + \sum_{i=1}^N [\,\texttt{mi\_llave}_i == \text{false}\,] = 1
    \]
    donde el corchete denota la función indicatriz de valor 1 si es cierta y 0 si es falsa.
    \item Inicialmente $\texttt{ocupado} = \text{false}$ y todas las variables locales tienen $\texttt{mi\_llave}_i = \text{true}$. La suma es $0 + 0 = 0$. Existe una única llave con valor \texttt{false} disponible en el sistema.
    \item La primitiva \texttt{swap} es atómica e indivisible a nivel de bus de hardware. El primer proceso que ejecuta \texttt{swap} extrae el valor \texttt{false} a su variable privada \texttt{mi\_llave}, mientras que la variable global \texttt{ocupado} pasa a valer \texttt{true}. Dicho proceso supera el bucle y entra a la SC.
    \item Mientras el recurso está ocupado ($\texttt{ocupado} = \text{true}$), cualquier otro proceso que ejecute \texttt{swap} intercambia su \texttt{mi\_llave} (\texttt{true}) por \texttt{ocupado} (\texttt{true}), reteniendo el valor \texttt{true} en su variable privada y continuando en espera activa.
    \item Como en ningún momento puede haber más de una variable local con valor \texttt{false}, a lo sumo un solo proceso puede encontrarse ejecutando la SC:
    \[
    N_{SC} \le 1 \quad \text{(Exclusión mutua garantizada)}
    \]
\end{itemize}

\textbf{3. Discusión de Progreso, Inanición y Equidad:}\\
\begin{itemize}[leftmargin=*]
    \item \textbf{Progreso:} Si ningún proceso está en la SC y $\texttt{ocupado} = \text{false}$, el primer proceso que ejecute \texttt{swap} adquiere la llave y accede. No puede producirse interbloqueo colectivo.
    \item \textbf{¿Basta la atomicidad de swap para asegurar equidad? NO.}
    La atomicidad de la instrucción sólo garantiza la indivisibilidad de un intercambio individual; \textbf{no impone ninguna disciplina temporal ni cola de espera FIFO} sobre los procesos contendientes.
    \item Cuando el proceso en SC sale y ejecuta $\texttt{ocupado} = \text{false}$, todos los procesos que esperan en su bucle compiten en una carrera asíncrona. La resolución depende del arbitraje del controlador de memoria y de la topología física (sistemas NUMA). Un proceso desfavorecido puede perder consecutivamente todas las contiendas y sufrir \textbf{inanición indefinida}. Para asegurar equidad se precisa un cerrojo por tickets (\emph{ticket lock}).
\end{itemize}

\textbf{4. Coste de Espera Ocupada y Optimización:}\\
La ejecución continua de \texttt{swap} genera continuas transacciones de invalidación en el protocolo de coherencia de caché (\emph{cache line bouncing}), saturando el bus de interconexión. Para mitigarlo se aplica el patrón \textbf{Test and Test-and-Set}: el proceso espera en un bucle pasivo leyendo en caché \texttt{while (ocupado) skip;} y sólo ejecuta \texttt{swap} cuando detecta que la variable ha pasado a valer \texttt{false}.
\end{solucion}

\begin{ejercicio}[59: Exclusión de Capacidad k mediante Cerrojo Atómico]
Un recurso admite simultáneamente a lo sumo $k$ procesos, con $1 \le k < N$. Diseñar las subrutinas \texttt{entrar()} y \texttt{salir()} para $N$ procesos utilizando únicamente una variable entera compartida \texttt{dentro}, inicialmente cero, y un cerrojo atómico \texttt{lock()} / \texttt{unlock()}. Se permite espera ocupada fuera del cerrojo. (a) Escribir pseudocódigo. (b) Demostrar el invariante $0 \le \text{dentro} \le k$. (c) Explicar por qué no debe mantenerse el cerrojo mientras se espera a que haya capacidad. (d) Discutir si la solución asegura ausencia de inanición.
\end{ejercicio}

\begin{solucion}
\textbf{Apartado (a): Pseudocódigo de las Subrutinas:}\\
\begin{lstlisting}[language=C++]
// Variables compartidas globales:
int dentro = 0;
Mutex cerrojo; // Primitivas atómicas lock() y unlock()

void entrar() {
    bool acceso_concedido = false;
    while (!acceso_concedido) {
        cerrojo.lock();
        if (dentro < k) {
            dentro = dentro + 1;
            acceso_concedido = true;
        }
        cerrojo.unlock();
        // Si no se concedio, el reintento se efectua fuera del cerrojo
    }
}

void salir() {
    cerrojo.lock();
    dentro = dentro - 1;
    cerrojo.unlock();
}
\end{lstlisting}

\textbf{Apartado (b): Demostración del Invariante $0 \le \text{dentro} \le k$:}\\
Demostraremos por inducción estructural sobre los estados del sistema:
\begin{itemize}[leftmargin=*]
    \item \textbf{Base inductiva:} Inicialmente $\texttt{dentro} = 0$. Como $1 \le k < N$, se cumple trivialmente $0 \le 0 \le k$.
    \item \textbf{Paso inductivo:} La variable \texttt{dentro} únicamente es modificada dentro de las secciones críticas protegidas por \texttt{cerrojo}:
    \begin{itemize}[leftmargin=*]
        \item En \texttt{entrar()}: Se evalúa $\texttt{dentro} < k$. Como \texttt{dentro} es entero, esto equivale a $\texttt{dentro} \le k-1$. Tras la asignación $\texttt{dentro}' = \texttt{dentro} + 1$, se cumple $\texttt{dentro}' \le k$. Además, como por hipótesis inductiva $\texttt{dentro} \ge 0$, tenemos $\texttt{dentro}' \ge 1 \ge 0$. Si la condición no se cumple, la variable no varía.
        \item En \texttt{salir()}: Por especificación, \texttt{salir()} sólo es invocada por procesos que previamente completaron \texttt{entrar()}. El número total de ejecuciones de \texttt{salir()} no puede superar al de \texttt{entrar()}, lo que garantiza $\texttt{dentro} \ge 1$ antes del decremento. Por ende, tras $\texttt{dentro}' = \texttt{dentro} - 1$, se cumple $\texttt{dentro}' \ge 0$. Puesto que $\texttt{dentro} \le k$, tenemos $\texttt{dentro}' \le k-1 < k$.
    \end{itemize}
    \item Queda formalmente demostrado el invariante de seguridad: $\forall t, \ 0 \le \text{dentro}(t) \le k$.
\end{itemize}

\textbf{Apartado (c): Por qué NO debe retenerse el cerrojo durante la espera:}\\
Si un proceso adquiriese el cerrojo y ejecutase el bucle de espera sin liberarlo:
\begin{lstlisting}[language=C++]
cerrojo.lock();
while (dentro >= k) { /* espera activa con cerrojo adquirido */ }
\end{lstlisting}
se produciría un \textbf{Interbloqueo Fatal (Deadlock)}:
\begin{itemize}[leftmargin=*]
    \item Ningún otro proceso podría adquirir \texttt{cerrojo}.
    \item Los procesos que se encuentran dentro del recurso no podrían ejecutar la subrutina \texttt{salir()}, puesto que \texttt{salir()} necesita adquirir \texttt{cerrojo} para decrementar \texttt{dentro}.
    \item Al ser imposible decrementar \texttt{dentro}, la condición $\texttt{dentro} \ge k$ permanecería eternamente cierta, congelando a todo el sistema.
    \item Por tanto, la liberación de \texttt{cerrojo} antes de reiterar la espera activa es estrictamente indispensable para el progreso del sistema.
\end{itemize}

\textbf{Apartado (d): Discusión sobre la Ausencia de Inanición:}\\
\textbf{La solución NO asegura la ausencia de inanición.}
Cuando la capacidad está colmada ($\texttt{dentro} = k$), múltiples procesos iteran concurrentemente en sus respectivos bucles \texttt{while (!acceso\_concedido)}. Cuando un proceso sale y decrementa la variable a $k-1$, el proceso que logra capturar el cerrojo y ocupar la plaza no sigue un orden de llegada FIFO, sino que depende del azar y del planificador. Procesos con menor prioridad de bus pueden ser adelantados arbitrariamente muchas veces, sufriendo inanición.
\end{solucion}

\begin{ejercicio}[60: Algoritmo de Turnos Circulares y Paso de Testigo en Anillo]
Para $N \ge 2$ procesos se comparte \texttt{s[0..N-1]}, inicialmente a cero. El proceso $P_i$ espera hasta que se cumpla $s[i] \ne s[i-1]$ si $i > 0$, o $s[0] = s[N-1]$ si $i = 0$. Al salir, ejecuta $s[i]:=s[i-1]$ si $i > 0$, o $s[0]:=1-s[0]$ si $i = 0$. (a) Examinar la exclusión mutua. (b) ¿Qué sucede si un proceso permanece indefinidamente en su sección no crítica? (c) Determinar si se cumple el requisito de progreso cuando solamente un proceso desea entrar. (d) Distinguir entre alternancia forzosa y equidad entre procesos contendientes.
\end{ejercicio}

\begin{solucion}
\textbf{Apartado (a): Examen Riguroso de la Exclusión Mutua:}\\
Definimos la condición de habilitación $E(i)$ que permite a $P_i$ acceder a la SC:
\[
E(0) \iff (s[0] = s[N-1]), \qquad E(i) \iff (s[i] \ne s[i-1]) \quad \forall i \in \{1, \dots, N-1\}
\]
\textbf{Lema de Proceso Distinguido Único:}\\
\emph{En cualquier configuración alcanzable del vector $s[0..N-1]$, existe exactamente un único proceso $k \in \{0, \dots, N-1\}$ tal que $E(k)$ es verdadera.}

\textbf{Demostración:}
\begin{itemize}[leftmargin=*]
    \item \textbf{Estado Inicial:} $s = [0, 0, \dots, 0]$.
    Para $i = 0$: $s[0] = s[N-1] \iff 0 = 0$ (\textbf{Verdadero}, $E(0)$ habilitado).
    Para todo $i > 0$: $s[i] \ne s[i-1] \iff 0 \ne 0$ (\textbf{Falso}). Único habilitado: $P_0$.
    \item Cuando $P_0$ sale, ejecuta $s[0] := 1 - s[0] = 1$. Vector: $[1, 0, 0, \dots, 0]$.
    Ahora $s[0] = s[N-1] \iff 1 = 0$ (Falso).
    Para $i = 1$: $s[1] \ne s[0] \iff 0 \ne 1$ (\textbf{Verdadero}, $E(1)$ habilitado).
    Para todo $i > 1$: $s[i] \ne s[i-1] \iff 0 \ne 0$ (Falso). Único habilitado: $P_1$.
    \item De forma inductiva, cuando $P_k$ ($k > 0$) sale y asigna $s[k] := s[k-1]$, inhabilita su propia condición e iguala su valor al de su predecesor, transfiriendo la habilitación de forma exclusiva al sucesor $P_{k+1}$ (o a $P_0$ si $k = N-1$).
    \item Como en todo instante exactamente un proceso tiene permiso de entrada, nunca pueden coexistir dos procesos en la SC:
    \[
    N_{SC} \le 1 \quad \text{(Exclusión mutua demostrada)}
    \]
\end{itemize}

\textbf{Apartado (b): Consecuencias si un proceso permanece en su Sección No Crítica (SNC):}\\
Si el proceso que ostenta la habilitación en un momento dado ($P_k$) se detiene o permanece indefinidamente en su sección no crítica (SNC) sin solicitar la entrada a la SC, nunca ejecutará el protocolo de salida ni actualizará la variable $s[k]$.
\begin{itemize}[leftmargin=*]
    \item En consecuencia, el testigo queda permanentemente retenido en $P_k$.
    \item Ningún otro proceso del anillo puede entrar jamás a la SC, violando directamente la \textbf{3.ª condición de Dijkstra} (un proceso en su SNC no debe interferir ni bloquear el acceso de los demás).
\end{itemize}

\textbf{Apartado (c): Cumplimiento del Requisito de Progreso con un Solo Proceso Interesado:}\\
\textbf{NO se cumple el requisito de progreso.}
Si únicamente el proceso $P_3$ desea entrar y todos los demás se hallan inactivos en su SNC, $P_3$ se verá incapaz de acceder hasta que $P_0, P_1$ y $P_2$ atraviesen secuencialmente sus respectivas secciones críticas. Al no haber competencia activa sobre el recurso y estar la SC desocupada, el sistema es incapaz de conceder el acceso inmediato al único proceso interesado.

\textbf{Apartado (d): Distinción entre Alternancia Forzosa y Equidad:}\\
\begin{itemize}[leftmargin=*]
    \item \textbf{Alternancia Forzosa (\emph{Strict Alternation}):} Impone un orden determinista y rígido fijado a priori ($P_0 \to P_1 \to \dots \to P_{N-1} \to P_0$), obligando a que cada proceso participe cíclicamente con independencia de si requiere o no el recurso. Si un proceso no tiene trabajo que realizar, paraliza a todos los demás.
    \item \textbf{Equidad (\emph{Fairness}):} Garantiza que entre los procesos que \textbf{efectivamente solicitan} la sección crítica, ninguno sufra postergación indefinida ni inanición. Permite que procesos activos adelanten a procesos que se encuentran pasivos en su SNC.
    \item El algoritmo analizado implementa alternancia forzosa, destruyendo la autonomía de ritmos entre procesos concurrentes.
\end{itemize}
\end{solucion}

\begin{ejercicio}[61: Protocolo de Tickets para Dos Procesos y Ruptura de Simetría]
Se comparten \texttt{n[0]=n[1]=0}. Cada $P(i)$, con $j=1-i$, ejecuta:
\begin{lstlisting}[language=C++]
n[i] := 1;
n[i] := n[j] + 1;
while n[j] != 0 and
    (n[j] < n[i] or (n[j] = n[i] and j < i)) do
    skip;
endwhile;
<seccion critica>;
n[i] := 0;
\end{lstlisting}
(a) Estudiar la exclusión mutua, considerando todas las intercalaciones relevantes de las asignaciones iniciales. (b) Analizar si el protocolo puede producir interbloqueo o inanición. (c) Estudiar qué ocurre al eliminar la asignación \texttt{n[i]:=1}. (d) Explicar la función del desempate por identificador. No suponer que la lectura de \texttt{n[j]} y la escritura posterior constituyen una operación indivisible.
\end{ejercicio}

\begin{solucion}
\textbf{Apartado (a): Exclusión Mutua bajo Intercalaciones Relevantes:}\\
La toma de ticket consta de dos operaciones no atómicas: (1) \texttt{n[i]:=1} (marcador de presencia), y (2) lectura de \texttt{n[j]} seguida de escritura \texttt{n[i]:=n[j]+1}. Analizamos los casos exhaustivos de intercalación:
\begin{itemize}[leftmargin=*]
    \item \textbf{Caso 1: Ejecución Secuencial (Sin Solapamiento):}\\
    $P_0$ ejecuta $n[0]:=1$ y luego $n[0]:=n[1]+1 = 0+1 = 1$. A continuación, $P_1$ lee $n[0]=1$ y asigna $n[1]:=1+1=2$. Los tickets son $(n[0]=1, n[1]=2)$.
    $P_0$ evalúa la guarda: $n[1]=2 < n[0]=1$ (Falso) $\implies P_0$ accede de inmediato.
    $P_1$ evalúa la guarda: $n[0]=1 < n[1]=2$ (\textbf{Verdadero}) $\implies P_1$ espera en el bucle hasta que $P_0$ libere la SC ($n[0]:=0$). Exclusión mutua garantizada.
    \item \textbf{Caso 2: Intercalación Concurrente Total (Empate de Tickets):}\\
    Ambos ejecutan $n[0]:=1$ y $n[1]:=1$. Ambos leen el valor 1 del rival y calculan su ticket a la vez: $n[0] := 1+1 = 2$ y $n[1] := 1+1 = 2$. Empate estricto: $n[0] = n[1] = 2$.
    \begin{itemize}[leftmargin=*]
        \item Guarda de $P_0$ ($i=0, j=1$): ¿$n[1] < n[0]$? ($2 < 2$, Falso). ¿$n[1] = n[0] \land 1 < 0$? ($2=2 \land \text{Falso}$, Falso). La condición es \textbf{Falsa} $\implies P_0$ entra a la SC.
        \item Guarda de $P_1$ ($i=1, j=0$): ¿$n[0] < n[1]$? ($2 < 2$, Falso). ¿$n[0] = n[1] \land 0 < 1$? ($2=2 \land \text{Verdadero}$, \textbf{Verdadero}). La condición es \textbf{Verdadera} $\implies P_1$ espera en el bucle.
    \end{itemize}
    El desempate favorece a $P_0$ de forma no ambigua: a lo sumo un proceso entra.
    \item \textbf{Caso 3: Intercalación Parcial:}\\
    Si un proceso lee el ticket intermedio 1 y el otro lee el definitivo, se obtienen valores estrictamente diferentes donde el menor ticket tiene prioridad absoluta.
\end{itemize}
Como el par ordenado $(n[i], i)$ define un orden total estricto irreflexivo, $N_{SC} \le 1$.

\textbf{Apartado (b): Ausencia de Interbloqueo e Inanición:}\\
\begin{itemize}[leftmargin=*]
    \item \textbf{Ausencia de Interbloqueo:} El predicado $(n[0], 0) < (n[1], 1)$ es asimétrico y transitivo; nunca puede ser verdadero simultáneamente para ambos procesos. Uno de los dos siempre encontrará su guarda en falso y accederá a la SC.
    \item \textbf{Ausencia de Inanición:} El proceso que espera en el bucle es liberado en cuanto el proceso en SC sale y ejecuta $n[i]:=0$. Si el proceso saliente desea reingresar, tomará un ticket $n_{\text{nuevo}} = n_{\text{espera}} + 1 > n_{\text{espera}}$, garantizando que el proceso que ya estaba esperando tendrá prioridad absoluta y entrará a la SC.
\end{itemize}

\textbf{Apartado (c): ¿Qué ocurre al eliminar la asignación \texttt{n[i]:=1}?:}\\
\textbf{SE DESTRUYE LA EXCLUSIÓN MUTUA.} Contraejemplo:
\begin{enumerate}[leftmargin=*,noitemsep]
    \item $P_0$ lee $n[1]$ (que vale 0) para calcular su ticket, pero es suspendido antes de escribir en $n[0]$.
    \item $P_1$ inicia su protocolo completo: lee $n[0]=0$, calcula y asigna $n[1] := 0+1 = 1$.
    \item $P_1$ evalúa la guarda: como $n[0] == 0$, la guarda es falsa y $P_1$ \textbf{entra a la Sección Crítica}.
    \item $P_0$ se reanuda y escribe su ticket pendiente: $n[0] := 0+1 = 1$.
    \item $P_0$ evalúa la guarda con $n[0]=1$ y $n[1]=1$: por desempate de identificador ($0 < 1$), $P_0$ tiene prioridad sobre $P_1$, saliendo del bucle.
    \item $P_0$ \textbf{entra a la Sección Crítica mientras $P_1$ sigue dentro}. Fallo fatal de exclusión mutua.
\end{enumerate}
La asignación $n[i]:=1$ actúa como un indicador transitorio (\emph{doorway}) que impide que el otro proceso crea falsamente que $P_i$ está inactivo.

\textbf{Apartado (d): Función del Desempate por Identificador:}\\
Dado que la lectura y la posterior suma no son atómicas, los procesos pueden obtener números de ticket idénticos. La relación lexicográfica estricta $(n[i] < n[j]) \lor (n[i] = n[j] \land i < j)$ rompe cualquier simetría determinísticamente, evitando estados de indecisión.
\end{solucion}

\begin{ejercicio}[62: Peterson para N Procesos: Filtro por Niveles y Cotas de Espera]
Considerar la generalización de Peterson con \texttt{nivel[i]} inicialmente cero y \texttt{victima[L]} compartidos. Cada proceso $P_i$ recorre los niveles $L = 1, \dots, N-1$:
\begin{lstlisting}[language=C++]
for L := 1 to N-1 do
    nivel[i] := L;
    victima[L] := i;
    while exists j != i such that
        (nivel[j] >= L and victima[L] = i) do skip;
endfor;
<seccion critica>;
nivel[i] := 0;
\end{lstlisting}
(a) Justificar por qué no pueden coexistir dos procesos en sección crítica. (b) Analizar si pueden encontrarse dos procesos en el nivel $N-2$ mientras ninguno está en $N-3$; razonar según la definición precisa de «estar en un nivel». (c) Examinar qué hipótesis adicionales serían necesarias para establecer cotas de espera. Evitar identificar automáticamente ausencia de inanición con espera acotada.
\end{ejercicio}

\begin{solucion}
\textbf{Apartado (a): Demostración de Exclusión Mutua (Lema del Filtro):}\\
El algoritmo organiza la contienda en $N-1$ etapas o filtros sucesivos.
\begin{itemize}[leftmargin=*]
    \item \textbf{Lema Fundamental del Filtro de Peterson:}\\
    \emph{En cualquier estado alcanzable, a lo sumo $N - L$ procesos pueden encontrarse en el nivel $L$ o en niveles superiores.}
    \item \textbf{Demostración por inducción sobre $L$:}
    \begin{itemize}[leftmargin=*]
        \item \emph{Base ($L = 1$):} En el nivel 1, la variable \texttt{victima[1]} almacena el identificador de un único proceso (el último en llegar). Este proceso no puede superar el bucle \texttt{while} mientras exista otro proceso con $\texttt{nivel}[j] \ge 1$. Por ende, al menos un proceso queda retenido en el nivel 1, permitiendo avanzar como máximo a $N - 1$ procesos.
        \item \emph{Paso Inductivo:} Asumamos que a lo sumo $N - L$ procesos pueden alcanzar el nivel $L$. En dicho nivel, la variable compartida \texttt{victima[L]} retiene obligatoriamente al último proceso en registrarse. En consecuencia, de los $N - L$ candidatos, al menos uno no puede franquear el bucle, permitiendo avanzar a lo sumo a $(N - L) - 1 = N - (L + 1)$ procesos al nivel $L+1$.
    \end{itemize}
    \item \textbf{Sección Crítica:} Para acceder a la SC, un proceso debe completar el nivel $L = N-1$. Aplicando el lema:
    \[
    N_{\text{procesos en SC}} \le N - (N - 1) = 1
    \]
    Por tanto, es imposible que dos procesos coexistan en la SC: $N_{SC} \le 1$.
\end{itemize}

\textbf{Apartado (b): ¿Pueden encontrarse dos procesos en $N-2$ y ninguno en $N-3$?:}\\
\textbf{Definición de «estar en el nivel $k$»:} Un proceso $P_i$ se encuentra en el nivel $k$ si ha ejecutado $\texttt{nivel}[i] := k$ y aún no ha ejecutado $\texttt{nivel}[i] := k+1$ (es decir, se encuentra ejecutando o esperando en la $k$-ésima iteración del bucle \texttt{for}).

\textbf{Respuesta: NO ES POSIBLE.}\\
\emph{Justificación Formal (Lema 3 de Peterson / Infomates Ejercicio 5.2.8):}
\begin{itemize}[leftmargin=*]
    \item Para que dos procesos $P_a$ y $P_b$ hayan superado el filtro del nivel $N-3$ y se encuentren simultáneamente en el nivel $N-2$, debió ocurrir que uno de ellos asumió la condición de víctima en $N-3$ mientras el otro avanzaba, o bien que un tercer proceso $P_c$ asumió el rol de víctima en dicho nivel.
    \item La invariante de distribución de procesos en los filtros de Peterson establece una propiedad monótona: para que existan $M \ge 2$ procesos en la etapa $k$, en cada una de las etapas previas $0, 1, \dots, k-1$ debe existir al menos un proceso actuando como víctima de retención.
    \item Si el nivel $N-3$ estuviera completamente vacío (0 procesos), significaría que no existe ningún proceso que retenga la variable \texttt{victima[N-3]}, lo que contradice el principio de avance del filtro. Por consiguiente, dicha configuración es inalcanzable.
\end{itemize}

\textbf{Apartado (c): Hipótesis Adicionales para Cotas de Espera frente a Ausencia de Inanición:}\\
\begin{itemize}[leftmargin=*]
    \item \textbf{Distinción conceptual:} La \emph{ausencia de inanición} es una propiedad cualitativa de vivacidad ($\forall i, \lozenge P_i^{SC}$). La \emph{espera acotada} es una propiedad cuantitativa de seguridad que acota uniformemente el número de adelantamientos por una función matemática determinista $f(N)$.
    \item \textbf{Hipótesis necesarias para derivar la cota de espera formal:}
    \begin{enumerate}[leftmargin=*]
        \item \textbf{Tiempo Finito en SC:} Todo proceso que entra en la SC sale de ella en un tiempo acotado por una constante finita ($\Delta_{SC} \le C_{SC} < \infty$).
        \item \textbf{Planificación Débilmente Justa en CPU:} Cada hilo activo en el protocolo de entrada progresa de forma continua en sus instrucciones.
        \item \textbf{Reingreso Cíclico sin Privilegios:} Todo proceso que abandone la SC y vuelva a solicitarla debe reiniciar su tránsito obligatoriamente desde el nivel $L=1$, garantizando que se colocará detrás (como nueva víctima) de los procesos rezagados en niveles inferiores.
    \end{enumerate}
    \item Bajo estas condiciones, se demuestra que un proceso compitiendo en el nivel $L$ espera a lo sumo a que cada uno de los demás procesos entre una vez por cada nivel superior, estableciendo una cota matemática de espera de $O(N^2)$ adelantamientos (exactamente $\frac{N(N-1)}{2}$ turnos).
\end{itemize}
\end{solucion}

\begin{ejercicio}[63: Algoritmo de Dijkstra para N Procesos: Análisis de Modificación de Guarda]
Se comparte \texttt{turno} y el vector \texttt{estado[i]} con valores \texttt{pasivo}, \texttt{solicitando} y \texttt{enSC}. En el algoritmo de Dijkstra estudiado en clase, durante el protocolo de entrada, un proceso que espera su turno ejecuta:
\begin{lstlisting}[language=C++]
while turno != i do
    if estado[turno] = pasivo then turno := i;
endwhile;
\end{lstlisting}
Se propone sustituir la guarda por \texttt{estado[turno] != enSC}, sin alterar el resto del algoritmo. (a) Comparar las dos condiciones. (b) Construir, si es posible, una ejecución que invalide alguna propiedad de corrección. (c) Precisar si el defecto afecta a la seguridad, al progreso o a la equidad. Para el análisis, utilizar el protocolo completo de Dijkstra presentado en clase, no únicamente el fragmento anterior.
\end{ejercicio}

\begin{solucion}
\textbf{1. Protocolo Canónico Completo de Dijkstra (1965) para N Procesos:}\\
\begin{lstlisting}[language=C++]
// Variables compartidas:
enum Estado { pasivo, solicitando, enSC };
Estado estado[N] = { pasivo, ..., pasivo };
int turno = 0;

// Protocolo para el proceso Pi:
void proceso(int i) {
    while (true) {
        // Protocolo de entrada:
        estado[i] = solicitando;
        L1: while (turno != i) {
            // Guarda original: if (estado[turno] == pasivo) turno = i;
            // Guarda propuesta:
            if (estado[turno] != enSC) {
                turno = i;
            }
        }
        estado[i] = enSC;
        for (int j = 0; j < N; ++j) {
            if (j != i && estado[j] == enSC) {
                goto L1; // Retroceso si detecta colision en SC
            }
        }

        // Seccion Critica:
        seccion_critica();

        // Protocolo de salida:
        estado[i] = pasivo;

        seccion_no_critica();
    }
}
\end{lstlisting}

\textbf{Apartado (a): Comparación Operativa de las Dos Condiciones:}\\
\begin{itemize}[leftmargin=*]
    \item \textbf{Condición Original (\texttt{estado[turno] == pasivo}):} Un proceso $P_i$ únicamente se apropia del turno (\texttt{turno := i}) si el titular actual no tiene interés en la sección crítica. Si el titular está en estado \texttt{solicitando}, los demás procesos respetan pacíficamente su turno y aguardan a que él concluya su entrada.
    \item \textbf{Condición Propuesta (\texttt{estado[turno] != enSC}):} El proceso $P_i$ puede arrebatar el turno no sólo si el titular está pasivo, sino \textbf{también cuando el titular está activamente compitiendo en el protocolo de entrada} (\texttt{estado[turno] == solicitando}), con tal de que no haya alcanzado todavía la SC.
\end{itemize}

\textbf{Apartado (b): Construcción del Contraejemplo (Interbloqueo Dinámico / Livelock):}\\
Consideremos $N = 2$ procesos ($P_0$ y $P_1$) con valor inicial $\texttt{turno} = 0$. Ambos solicitan entrar:
\begin{center}
\resizebox{\linewidth}{!}{%
\begin{tabular}{cllcccp{4.2cm}}
\toprule
\textbf{Paso} & \textbf{Proceso} & \textbf{Línea Ejecutada} & $\text{est}[0]$ & $\text{est}[1]$ & \textbf{turno} & \textbf{Efecto en el Sistema} \\ \midrule
1 & $P_0$ & $\texttt{estado}[0] := \text{solicitando}$ & sol & pas & 0 & $P_0$ inicia solicitud. \\
2 & $P_1$ & $\texttt{estado}[1] := \text{solicitando}$ & sol & sol & 0 & $P_1$ inicia solicitud. \\

\multicolumn{7}{c}{\textbf{CICLO INFINITO: Ningún proceso logra validar $\texttt{turno} == i$ para pasar a $\text{enSC}$. LIVELOCK TOTAL.}} \\

Ambos procesos se disputan el turno de forma destructiva y oscilante, impidiendo que ninguno complete la verificación de entrada.

\textbf{Apartado (c): Clasificación del Defecto (Seguridad vs. Progreso vs. Equidad):}\\
\begin{itemize}[leftmargin=*]
    \item \textbf{Seguridad (Exclusión Mutua): NO SE VE AFECTADA.}
    La exclusión mutua estricta en el algoritmo de Dijkstra está custodiada por la segunda barrera (el bucle \texttt{for} que verifica si algún otro proceso tiene $\texttt{estado}[j] == \text{enSC}$, retrocediendo con \texttt{goto L1} si detecta concurrencia). El cambio en la primera guarda no permite que dos procesos superen juntos este segundo filtro.
    \item \textbf{Progreso (Ausencia de Interbloqueo): QUEDA COMPLETAMENTE DESTRUIDO.}
    El defecto provoca un \textbf{fallo catastrófico de progreso} (vivacidad global del sistema). La sección crítica se encuentra desocupada y dos procesos compiten activamente por acceder, pero el sabotaje mutuo sobre la variable \texttt{turno} les impide entrar indefinidamente.
    \item \textbf{Equidad:} Se degrada como consecuencia del fallo de progreso.
\end{itemize}
\end{solucion}
