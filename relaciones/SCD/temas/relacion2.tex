\begin{ejercicio}[37: Coordinación de Secuencias de Procesos con Semáforos]
Tres procesos ejecutan indefinidamente las siguientes secuencias:
\begin{lstlisting}[language=C++]
process P1: while true do begin a; b; c end
process P2: while true do begin d; e; f end
process P3: while true do begin g; h; i end
\end{lstlisting}
Resolver independientemente mediante semáforos los siguientes requisitos. En (a)--(c), la condición se refiere a la misma ronda $k$ de ejecución de cada proceso, numerada desde 1; evitar que señales de rondas futuras satisfagan esperas de rondas anteriores. Si una solución exige sincronización de fin de ronda, explicitarla:
\begin{enumerate}[label=(\alph*)]
    \item $P_2$ ejecuta $e_k$ solamente después de que haya terminado $a_k$ o $g_k$ (basta una de las dos).
    \item $P_2$ ejecuta $e_k$ solamente después de que hayan terminado $a_k$ y $g_k$.
    \item $P_2$ ejecuta $e_k$ y $P_3$ ejecuta $h_k$ solamente después de que $P_1$ haya terminado $b_k$; ambas autorizaciones son independientes.
    \item A lo sumo dos de las operaciones $b$, $f$ y $h$ pueden estar ejecutándose simultáneamente.
\end{enumerate}
\end{ejercicio}

\begin{solucion}
\textbf{Apartado (a): OR Lógico ($a_k$ o $g_k$ habilita $e_k$ en la ronda $k$):}\\
Para evitar que si ambos terminan se generen dos fichas en el semáforo (lo que satisfaría espuriamente la ronda $k+1$), se utiliza una variable protegida \texttt{notificado} por ronda y una barrera de fin de ronda:
\begin{lstlisting}[language=C++]
sem_t sem_e = 0;        // Autoriza a P2 a ejecutar e
sem_t mutex = 1;        // Protege la variable notificado
sem_t fin_ronda_1 = 0, fin_ronda_3 = 0; // Sincronizacion de fin de ronda
bool notificado = false;

// Proceso P1:
while (true) {
    a();
    sem_wait(&mutex);
    if (!notificado) { notificado = true; sem_post(&sem_e); }
    sem_post(&mutex);
    b(); c();
    sem_wait(&fin_ronda_1); // Espera a que P2 complete la ronda
}

// Proceso P2:
while (true) {
    d();
    sem_wait(&sem_e);   // Espera autorizacion de a o de g
    e();
    f();
    sem_wait(&mutex);
    notificado = false; // Reset para la siguiente ronda k+1
    sem_post(&mutex);
    sem_post(&fin_ronda_1);
    sem_post(&fin_ronda_3);
}

// Proceso P3:
while (true) {
    g();
    sem_wait(&mutex);
    if (!notificado) { notificado = true; sem_post(&sem_e); }
    sem_post(&mutex);
    h(); i();
    sem_wait(&fin_ronda_3);
}
\end{lstlisting}

\textbf{Apartado (b): AND Lógico ($a_k$ y $g_k$ deben terminar antes de $e_k$):}\\
Se requieren dos semáforos binarios independientes inicializados a 0, y $P_2$ ejecuta sendos \texttt{wait}:
\begin{lstlisting}[language=C++]
sem_t sem_a = 0, sem_g = 0;
sem_t fin_ronda_1 = 0, fin_ronda_3 = 0;

// P1: a(); sem_post(&sem_a); b(); c(); sem_wait(&fin_ronda_1);
// P3: g(); sem_post(&sem_g); h(); i(); sem_wait(&fin_ronda_3);
// P2: d(); sem_wait(&sem_a); sem_wait(&sem_g); e(); f();
//     sem_post(&fin_ronda_1); sem_post(&fin_ronda_3);
\end{lstlisting}

\textbf{Apartado (c): Bifurcación independiente tras $b_k$ (habilita $e_k$ y $h_k$):}\\
$P_1$ notifica a través de dos semáforos distintos y espera a que ambos procesos completen su uso antes de pasar a la ronda $k+1$:
\begin{lstlisting}[language=C++]
sem_t sem_p2 = 0, sem_p3 = 0;
sem_t fin_p2 = 0, fin_p3 = 0;

// P1: a(); b(); sem_post(&sem_p2); sem_post(&sem_p3); c(); sem_wait(&fin_p2); sem_wait(&fin_p3);
// P2: d(); sem_wait(&sem_p2); e(); f(); sem_post(&fin_p2);
// P3: g(); sem_wait(&sem_p3); h(); i(); sem_post(&fin_p3);
\end{lstlisting}

\textbf{Apartado (d): A lo sumo 2 operaciones de $\{b, f, h\}$ simultáneas:}\\
Este es el patrón canónico de exclusión mutua generalizada ($N$-aforo). Se define un \textbf{semáforo contador inicializado a 2}:
\begin{lstlisting}[language=C++]
sem_t aforo_bfh = 2; // Invariante: 0 <= aforo_bfh <= 2

// En P1: a(); sem_wait(&aforo_bfh); b(); sem_post(&aforo_bfh); c();
// En P2: d(); e(); sem_wait(&aforo_bfh); f(); sem_post(&aforo_bfh);
// En P3: g(); sem_wait(&aforo_bfh); h(); sem_post(&aforo_bfh); i();
\end{lstlisting}
\textbf{Invariante de seguridad:} En todo instante se cumple:
\[
(\text{en\_b} + \text{en\_f} + \text{en\_h}) + \text{valor}(aforo\_bfh) = 2 \implies \text{en\_b} + \text{en\_f} + \text{en\_h} \le 2.
\]
\end{solucion}

\begin{ejercicio}[38: Productor-Consumidor sobre Variable Simple]
Dos procesos comparten la variable global $x$. Las constantes $n$ y $c$ son inmutables; $m$ y $d$ son locales:
\begin{lstlisting}[language=C++]
process P1: while true do begin m := 2*x - n; imprimir(m); end
process P2: while true do begin d := leer_teclado(); x := d - 5*c; end
\end{lstlisting}
Diseñar dos protocolos mediante semáforos:
\begin{enumerate}[label=(\alph*)]
    \item Consumir exactamente una vez todos los valores producidos, en orden y sin sobrescrituras.
    \item Consumir exactamente los valores de orden impar ($1, 3, 5, \dots$), descartando los de orden par, sin duplicaciones ni lecturas inconsistentes.
\end{enumerate}
\end{ejercicio}

\begin{solucion}
\textbf{Apartado (a): Consumo 1 a 1 de todos los valores:}\\
Se utilizan dos semáforos binarios que forman un cerrojo alternante (\emph{ping-pong}):
\begin{lstlisting}[language=C++]
sem_t libre = 1;     // P2 puede producir
sem_t ocupado = 0;   // P1 puede consumir

// Proceso P1 (Consumidor):
while (true) {
    sem_wait(&ocupado);
    m = 2 * x - n;
    sem_post(&libre);
    imprimir(m);
}

// Proceso P2 (Productor):
while (true) {
    d = leer_teclado();
    sem_wait(&libre);
    x = d - 5 * c;
    sem_post(&ocupado);
}
\end{lstlisting}
$P_2$ se bloquea si produce un valor antes de que $P_1$ lo consuma. Se garantiza que cada valor producido se consume exactamente una vez en orden.

\textbf{Apartado (b): Consumo exclusivo de los valores de orden impar ($1, 3, 5, \dots$):}\\
$P_2$ cuenta las producciones mediante una variable local. Si la producción es par, no avisa a $P_1$; si es impar, avisa y espera lectura:
\begin{lstlisting}[language=C++]
sem_t libre = 1;
sem_t ocupado = 0;

// Proceso P1 (Consumidor):
while (true) {
    sem_wait(&ocupado); // Solo despierta en valores impares
    m = 2 * x - n;
    sem_post(&libre);
    imprimir(m);
}

// Proceso P2 (Productor):
int orden = 0;
while (true) {
    d = leer_teclado();
    orden++;
    if (orden % 2 != 0) {
        // Valor impar: debe ser consumido obligatoriamente por P1
        sem_wait(&libre);
        x = d - 5 * c;
        sem_post(&ocupado);
    } else {
        // Valor par: se descarta sin que P1 lo consuma
        sem_wait(&libre);
        x = d - 5 * c;
        sem_post(&libre); // Se libera inmediatamente para la siguiente produccion
    }
}
\end{lstlisting}
\end{solucion}

\begin{ejercicio}[39: El Aseo Compartido con Semáforos POSIX]
Un aseo admite simultáneamente o bien una mujer o bien hasta cinco hombres; nunca ambos a la vez. Resolver con semáforos POSIX no nombrados:
\begin{enumerate}[label=(\alph*)]
    \item Prioridad estricta de hombres: si hay hombres esperando, ninguna mujer nueva puede entrar, incluso si el aforo masculino está completo.
    \item Prioridad estricta de mujeres: si hay mujeres esperando, ningún hombre nuevo puede entrar.
\end{enumerate}
\end{ejercicio}

\begin{solucion}
Se modela la variante (a) (Prioridad a Hombres). Se mantienen contadores protegidos para hombres dentro ($H$), hombres esperando ($H_{esp}$), mujeres dentro ($M$) y mujeres esperando ($M_{esp}$):
\begin{lstlisting}[language=C++]
sem_t mutex = 1;
sem_t sem_hombres = 0;
sem_t sem_mujeres = 0;
int H = 0, H_esp = 0;
int M = 0, M_esp = 0;

void entrar_hombre() {
    sem_wait(&mutex);
    H_esp++;
    // Puede entrar si no hay mujeres dentro y hay menos de 5 hombres
    if (M == 0 && H < 5) {
        H_esp--;
        H++;
        sem_post(&sem_hombres);
    }
    sem_post(&mutex);
    sem_wait(&sem_hombres);
}

void salir_hombre() {
    sem_wait(&mutex);
    H--;
    // Si quedan hombres esperando, entra el siguiente hombre
    if (H_esp > 0 && H < 5) {
        H_esp--;
        H++;
        sem_post(&sem_hombres);
    } else if (H == 0 && H_esp == 0 && M_esp > 0) {
        // Si no quedan hombres, pasa una mujer
        M_esp--;
        M = 1;
        sem_post(&sem_mujeres);
    }
    sem_post(&mutex);
}

void entrar_mujer() {
    sem_wait(&mutex);
    // Prioridad a hombres: solo entra si H == 0, M == 0 y NO hay hombres esperando
    if (H == 0 && M == 0 && H_esp == 0) {
        M = 1;
        sem_post(&sem_mujeres);
    } else {
        M_esp++;
    }
    sem_post(&mutex);
    sem_wait(&sem_mujeres);
}

void salir_mujer() {
    sem_wait(&mutex);
    M = 0;
    // Tienen prioridad los hombres que esperan
    if (H_esp > 0) {
        int a_despertar = std::min(H_esp, 5);
        H_esp -= a_despertar;
        H += a_despertar;
        for (int k = 0; k < a_despertar; k++) sem_post(&sem_hombres);
    } else if (M_esp > 0) {
        M_esp--;
        M = 1;
        sem_post(&sem_mujeres);
    }
    sem_post(&mutex);
}
\end{lstlisting}
\textbf{Discusión sobre Inanición:} La prioridad estricta causa \textbf{inanición de mujeres} si el flujo de llegada de hombres es continuo ($H_{esp} > 0$). Los semáforos POSIX no garantizan política FIFO en el desbloqueo, por lo que dentro de la misma clase el planificador del kernel puede elegir arbitrariamente.
\end{solucion}

\begin{ejercicio}[40: Reentrancia frente a Exclusión Mutua en Monitores]
Un monitor garantiza exclusión mutua al ejecutar sus procedimientos. Explicar qué significa que un procedimiento sea reentrante, por qué exclusión mutua y reentrancia no son equivalentes y en qué situaciones es necesario exigir reentrancia. Distinguir la semántica de señales Hoare (SU) y Mesa (SC).
\end{ejercicio}

\begin{solucion}
\begin{itemize}[leftmargin=*]
    \item \textbf{Definición de Reentrancia:} Un código es reentrante si puede ser interrumpido a mitad de su ejecución por otro hilo (o por una llamada recursiva/señal) y reanudado posteriormente sin que su estado lógico resulte alterado. Para ello, \textbf{no debe modificar variables estáticas o globales no protegidas} y debe almacenar su estado local exclusivamente en la pila (\emph{stack}) del hilo invocador.
    \item \textbf{No equivalencia con Exclusión Mutua:} La exclusión mutua restringe el acceso a un solo hilo a la vez, pero no previene que si un procedimiento realiza una llamada recursiva sobre sí mismo o cede el monitor en un \texttt{wait}, el estado local sea sobreescrito si reside en memoria estática.
    \item \textbf{Situaciones donde se exige reentrancia:}
    \begin{enumerate}
        \item Cuando un hilo en un monitor invoca \texttt{c.wait()} o \texttt{c.signal()}: el hilo cede el monitor y otro hilo puede entrar al mismo procedimiento. Si las variables locales estuvieran en variables globales del monitor, el nuevo hilo las destruiría.
        \item Invocaciones cruzadas o recursivas entre procedimientos del monitor.
    \end{enumerate}
    \item \textbf{Diferencia entre SU y SC:}
    \begin{itemize}
        \item \textbf{SU (Hoare):} El señalador pasa a la cola urgente y el despertado entra de inmediato. La condición lógica se garantiza intacta tras \texttt{wait} (basta \texttt{if (!cond) wait()}).
        \item \textbf{SC (Mesa):} El señalador retiene el monitor y el despertado va a la cola de entrada. La condición puede ser invalidada por otro hilo antes de que el despertado tome el control, haciendo \textbf{obligatorio el bucle} \texttt{while (!cond) wait()}.
    \end{itemize}
\end{itemize}
\end{solucion}

\begin{ejercicio}[41: Dos Tipos de Recursos Indistinguibles y Prevención de Interbloqueo]
Un sistema dispone de $N_1 > 0$ unidades de recurso tipo 1 y $N_2 > 0$ de tipo 2. Demostrar cómo surge interbloqueo y diseñar un monitor que lo evite.
\end{ejercicio}

\begin{solucion}
\textbf{1. Escenario de Interbloqueo:}\\
Si el proceso $A$ pide primero 1 unidad de $N_1$ y luego 1 de $N_2$, mientras que el proceso $B$ pide primero 1 de $N_2$ y luego 1 de $N_1$, se puede llegar al estado donde $N_1$ y $N_2$ quedan agotados: $A$ retiene $N_1$ y espera $N_2$, y $B$ retiene $N_2$ y espera $N_1$. Cumple las 4 condiciones de Coffman $\implies$ \textbf{Interbloqueo circular}.

\textbf{2. Diseño del Monitor con Asignación Atómica (\texttt{HoareMonitor} UGR):}
\begin{lstlisting}[language=C++]
#include "scd.h"
using namespace std;
using namespace scd;

class MonitorRecursos : public HoareMonitor {
private:
    CondVar cola;
    int     libres1, libres2;

public:
    MonitorRecursos(int n1, int n2) : libres1(n1), libres2(n2) {
        cola = newCondVar();
    }

    void adquirir(int p1, int p2) {
        // En semantica SU basta 'if': asignacion atomica (todo o nada)
        if (libres1 < p1 || libres2 < p2) {
            cola.wait();
        }
        libres1 -= p1;
        libres2 -= p2;
    }

    void liberar(int l1, int l2) {
        libres1 += l1;
        libres2 += l2;
        cola.signal(); // Despertar al siguiente solicitante bloqueado
    }
};
\end{lstlisting}
Al concederse los recursos de forma atómica (\emph{all-or-nothing}), se destruye la condición de Coffman de \textbf{retención y espera}, impidiendo formalmente el interbloqueo.
\end{solucion}

\begin{ejercicio}[42: Lectores-Escritores con Monitores]
Resolver el problema de lectores y escritores mediante monitores con prioridad a escritores y con política equitativa sin inanición.
\end{ejercicio}

\begin{solucion}
\textbf{Implementación Oficial UGR (\texttt{HoareMonitor} y \texttt{CondVar} de \texttt{scd.h}):}\\
Bajo semántica SU (Hoare), la exclusión mutua es automática y las variables de condición \texttt{CondVar} garantizan orden FIFO. En la variante con prioridad a escritores, si hay algún escritor escribiendo o esperando turno, los nuevos lectores deben suspenderse:
\begin{lstlisting}[language=C++]
#include "scd.h"
using namespace std;
using namespace scd;

class LectoresEscritoresPrioridadEscritores : public HoareMonitor {
private:
    int     n_lec;              // Numero de lectores leyendo actualmente
    bool    escrib;             // true si hay un escritor escribiendo
    int     escrib_esperando;   // Numero de escritores esperando turno
    CondVar cola_lectores;
    CondVar cola_escritores;

public:
    LectoresEscritoresPrioridadEscritores() : n_lec(0), escrib(false), escrib_esperando(0) {
        cola_lectores   = newCondVar();
        cola_escritores = newCondVar();
    }

    void iniciar_lectura() {
        if (escrib || escrib_esperando > 0) {
            cola_lectores.wait();
        }
        n_lec++;
        cola_lectores.signal(); // Cascada SU para lectores en espera
    }

    void fin_lectura() {
        n_lec--;
        if (n_lec == 0) {
            cola_escritores.signal(); // Despertar al escritor prioritario
        }
    }

    void iniciar_escritura() {
        escrib_esperando++;
        if (escrib || n_lec > 0) {
            cola_escritores.wait();
        }
        escrib_esperando--;
        escrib = true;
    }

    void fin_escritura() {
        escrib = false;
        if (escrib_esperando > 0) {
            cola_escritores.signal();
        } else {
            cola_lectores.signal();
        }
    }
};
\end{lstlisting}
\end{solucion}

\begin{ejercicio}[43: Puente de un Solo Carril con Cupo Máximo]
Vehículos del norte y del sur cruzan un puente de un solo carril.
\begin{enumerate}[label=(\alph*)]
    \item Monitor básico y discusión de inanición.
    \item Modificación para conceder turnos de hasta diez entradas consecutivas cuando hay espera opuesta.
\end{enumerate}
\end{ejercicio}

\begin{solucion}
\textbf{Apartado (a):} En la política básica (entran del norte si no hay coches del sur cruzando), si llega un flujo ininterrumpido de coches del norte, los coches del sur sufrirán \textbf{inanición indefinida}.

\textbf{Apartado (b): Monitor Canónico en C++11 con \texttt{HoareMonitor} (UGR):}
\begin{lstlisting}[language=C++]
#include "scd.h"
using namespace std;
using namespace scd;

class MonitorPuenteCupo : public HoareMonitor {
private:
    int     coches_cruzando;  // Numero de vehiculos en el puente
    int     sentido_actual;   // 0: vacio, 1: Norte, 2: Sur
    int     esperando_norte;  // Vehiculos esperando en el Norte
    int     esperando_sur;    // Vehiculos esperando en el Sur
    int     cupo_actual;      // Vehiculos que han entrado en la tanda actual (max 10)
    CondVar cola_norte;
    CondVar cola_sur;

public:
    MonitorPuenteCupo() : coches_cruzando(0), sentido_actual(0), 
                          esperando_norte(0), esperando_sur(0), cupo_actual(0) {
        cola_norte = newCondVar();
        cola_sur   = newCondVar();
    }

    void entrarNorte() {
        esperando_norte++;
        if ((sentido_actual == 2 && coches_cruzando > 0) ||
            (sentido_actual == 1 && cupo_actual >= 10 && esperando_sur > 0)) {
            cola_norte.wait();
        }
        esperando_norte--;
        sentido_actual = 1;
        coches_cruzando++;
        cupo_actual++;

        if (cupo_actual < 10 && esperando_norte > 0) {
            cola_norte.signal();
        }
    }

    void salirNorte() {
        coches_cruzando--;
        if (coches_cruzando == 0) {
            if (cupo_actual >= 10 || esperando_norte == 0) {
                cupo_actual = 0;
                sentido_actual = (esperando_sur > 0) ? 2 : 0;
                cola_sur.signal();
            } else {
                cola_norte.signal();
            }
        }
    }

    void entrarSur() {
        esperando_sur++;
        if ((sentido_actual == 1 && coches_cruzando > 0) ||
            (sentido_actual == 2 && cupo_actual >= 10 && esperando_norte > 0)) {
            cola_sur.wait();
        }
        esperando_sur--;
        sentido_actual = 2;
        coches_cruzando++;
        cupo_actual++;

        if (cupo_actual < 10 && esperando_sur > 0) {
            cola_sur.signal();
        }
    }

    void salirSur() {
        coches_cruzando--;
        if (coches_cruzando == 0) {
            if (cupo_actual >= 10 || esperando_sur == 0) {
                cupo_actual = 0;
                sentido_actual = (esperando_norte > 0) ? 1 : 0;
                cola_norte.signal();
            } else {
                cola_sur.signal();
            }
        }
    }
};
\end{lstlisting}
\end{solucion}

\begin{ejercicio}[44: La Olla de los Salvajes y el Cocinero]
Olla de capacidad $M > 0$ raciones y $N > 0$ comensales. El primer salvaje que encuentra la olla vacía despierta al cocinero; el resto espera sin generar nuevas llamadas. Diseñar el monitor con semántica SU.
\end{ejercicio}

\begin{solucion}
\begin{lstlisting}[language=C++]
Monitor Olla {
    int raciones = M;      // Capacidad inicial llena
    cond cola_salvajes;
    cond cola_cocinero;
    bool aviso_enviado = false;

    procedure servir() {
        // En semantica SU, basta un if porque la senal reactiva de inmediato
        if (raciones == 0) {
            if (!aviso_enviado) {
                aviso_enviado = true;
                cola_cocinero.signal(); // Despierta al cocinero (pasa a cola urgente)
            }
            cola_salvajes.wait();
        }
        raciones = raciones - 1;
        if (raciones > 0) {
            cola_salvajes.signal(); // Efecto cascada: avisa al siguiente salvaje
        }
    }

    procedure esperarPeticion() {
        if (!aviso_enviado) {
            cola_cocinero.wait();
        }
    }

    procedure reponer() {
        raciones = M;
        aviso_enviado = false;
        cola_salvajes.signal(); // Despierta al primer salvaje en espera
    }
}
\end{lstlisting}
\textbf{Invariante:} $0 \le raciones \le M$. Si $raciones == 0$, ningún salvaje puede completar \texttt{servir()} antes de que el cocinero reponga.
\end{solucion}

\begin{ejercicio}[45: Cuenta Bancaria Compartida con Saldo No Negativo]
Saldo inicial $S_0 \ge 0$. Procedimientos \texttt{ingresar(c)} y \texttt{retirar(c)} ($c > 0$). Resolver bajo políticas:
\begin{enumerate}[label=(\alph*)]
    \item Concesión en cuanto hay saldo suficiente (con colas normales y con colas de prioridad por importe solicitado).
    \item Orden estricto de llegada (FIFO).
\end{enumerate}
\end{ejercicio}

\begin{solucion}
\textbf{Apartado (a.2): Cola de prioridad por importe solicitado ($c$ mínimo primero):}\\
Bajo semántica SU, se utiliza una variable condición con prioridad ordenada por el importe $c$:
\begin{lstlisting}[language=C++]
Monitor CuentaAhorrosPrioridadImporte {
    int saldo = S0;
    cond_p cola_retiradas; // Cola de condicion con prioridad por c

    procedure ingresar(int c) {
        saldo = saldo + c;
        // Despertar mientras haya fondos para el que pide menos
        while (!cola_retiradas.empty() && cola_retiradas.min_p() <= saldo) {
            cola_retiradas.signal();
        }
    }

    procedure retirar(int c) {
        if (saldo < c) {
            cola_retiradas.wait(c); // Se suspende con prioridad = c
        }
        saldo = saldo - c;
        if (!cola_retiradas.empty() && cola_retiradas.min_p() <= saldo) {
            cola_retiradas.signal();
        }
    }
}
\end{lstlisting}

\textbf{Apartado (b): Orden estricto de llegada (FIFO con Ticket):}\\
\begin{lstlisting}[language=C++]
Monitor CuentaFIFO {
    int saldo = S0;
    int ticket_turno = 0;
    int ticket_siguiente = 0;
    cond cola_espera;

    procedure ingresar(int c) {
        saldo = saldo + c;
        cola_espera.signal_all(); // Notifica para que el del turno revalide
    }

    procedure retirar(int c) {
        int mi_ticket = ticket_siguiente++;
        while (mi_ticket != ticket_turno || saldo < c) {
            cola_espera.wait();
        }
        saldo = saldo - c;
        ticket_turno++;
        cola_espera.signal_all();
    }
}
\end{lstlisting}
\end{solucion}

\begin{ejercicio}[46: Recurso Indivisible con Prioridades y Envejecimiento]
$n \ge 1$ procesos comparten un recurso $R$. Cada $P_i$ tiene prioridad fija $i$ (índice menor = mayor prioridad). Diseñar monitor y política de envejecimiento para evitar inanición.
\end{ejercicio}

\begin{solucion}
\begin{lstlisting}[language=C++]
Monitor RecursoPrioridad {
    bool ocupado = false;
    cond_p cola_espera; // Cola ordenada por prioridad efectiva

    procedure solicitar(int id, int prioridad_base) {
        if (ocupado) {
            cola_espera.wait(prioridad_base);
        }
        ocupado = true;
    }

    procedure liberar() {
        ocupado = false;
        if (!cola_espera.empty()) {
            cola_espera.signal(); // Despierta al de menor indice numerico
        }
    }
}
\end{lstlisting}
\textbf{Envejecimiento (\emph{Aging}):} Si llegan continuamente procesos de prioridad alta, los de prioridad baja sufren inanición. Para impedirlo, cada vez que un proceso completa el recurso, se decrementa en 1 unidad la prioridad efectiva de todos los procesos que continúen esperando en la cola (\texttt{prioridad\_efectiva = max(1, prioridad\_base - esperas)}), garantizando que cualquier petición alcanzará eventualmente la máxima prioridad (ausencia de inanición).
\end{solucion}

\begin{ejercicio}[47: Barrera Cíclica de Dos Participantes (Semáforos Puros)]
Implementar una barrera cíclica reutilizable para dos hilos utilizando exclusivamente semáforos y contadores. Evitar que una señal de la ronda $k$ libere erróneamente a un hilo de la ronda $k+1$.
\end{ejercicio}

\begin{solucion}
Se utiliza el esquema clásico del \textbf{Doble Torniquete} (\emph{Two-Turnstile}):
\begin{lstlisting}[language=C++]
sem_t mutex = 1;
sem_t torniquete1 = 0;
sem_t torniquete2 = 1; // Segundo torniquete cerrado para la fase de salida
int contador = 0;

void llegar() {
    // FASE 1: Llegada y bloqueo
    sem_wait(&mutex);
    contador++;
    if (contador == 2) {
        sem_wait(&torniquete2); // Bloquea la salida de la fase previa
        sem_post(&torniquete1); // Abre el paso del primer torniquete
    }
    sem_post(&mutex);

    sem_wait(&torniquete1); // Espera de fase
    sem_post(&torniquete1); // Cascada

    // FASE 2: Salida y preparacion para la siguiente ronda
    sem_wait(&mutex);
    contador--;
    if (contador == 0) {
        sem_wait(&torniquete1); // Cierra el primer torniquete
        sem_post(&torniquete2); // Abre el segundo torniquete
    }
    sem_post(&mutex);

    sem_wait(&torniquete2);
    sem_post(&torniquete2);
}
\end{lstlisting}
El segundo torniquete impide que el primer hilo que supere la barrera complete la siguiente ronda e interactúe con el contador antes de que el segundo hilo haya salido de la ronda actual.
\end{solucion}

\begin{ejercicio}[48: Los Cinco Filósofos Comensales con Monitor]
Cinco filósofos comparten 5 tenedores.
\begin{enumerate}[label=(\alph*)]
    \item Adquisición individual en monitor y corrección de la liberación.
    \item Ejecución con interbloqueo.
    \item Prevención mediante limitación de aforo a 4 filósofos.
\end{enumerate}
\end{ejercicio}

\begin{solucion}
\textbf{Apartado (a) y (b): Interbloqueo Circular:}\\
Si cada filósofo $i$ toma primero su tenedor izquierdo $T_i$, todos los 5 filósofos retienen un tenedor y esperan el derecho $T_{(i+1)\%5}$. Hay un ciclo de espera cerrada $\implies$ \textbf{Interbloqueo}.

\textbf{Apartado (c): Solución con Aforo de 4 Filósofos (\texttt{HoareMonitor} UGR):}
\begin{lstlisting}[language=C++]
#include "scd.h"
using namespace std;
using namespace scd;

class MonitorFilosofosAforo : public HoareMonitor {
private:
    CondVar cola_aforo;
    CondVar cola_tenedores[5];
    bool    tenedor_libre[5] = {true, true, true, true, true};
    int     sentados_o_esperando = 0;

public:
    MonitorFilosofosAforo() {
        cola_aforo = newCondVar();
        for (int i = 0; i < 5; i++) {
            cola_tenedores[i] = newCondVar();
        }
    }

    void entrar_a_comer(int i) {
        if (sentados_o_esperando >= 4) {
            cola_aforo.wait();
        }
        sentados_o_esperando++;

        if (!tenedor_libre[i]) {
            cola_tenedores[i].wait();
        }
        tenedor_libre[i] = false;

        if (!tenedor_libre[(i + 1) % 5]) {
            cola_tenedores[(i + 1) % 5].wait();
        }
        tenedor_libre[(i + 1) % 5] = false;
    }

    void salir_de_comer(int i) {
        tenedor_libre[i] = true;
        tenedor_libre[(i + 1) % 5] = true;
        
        cola_tenedores[i].signal();
        cola_tenedores[(i + 1) % 5].signal();

        sentados_o_esperando--;
        cola_aforo.signal();
    }
};
\end{lstlisting}
Por el Principio del Palomar, con 4 filósofos y 5 tenedores, al menos uno tendrá disponibles sus dos tenedores contiguos, garantizando \textbf{ausencia absoluta de interbloqueo}.
\end{solucion}

\begin{ejercicio}[49: Canal Acotado con Cierre y Terminación Limpia]
Canal de capacidad $K \ge 1$ con $p \ge 2$ productores y $q \ge 2$ consumidores. Implementar con semáforos un mecanismo de cierre sin marcadores centinela que desbloquee limpiamente a todos los consumidores al vaciarse.
\end{ejercicio}

\begin{solucion}
\begin{lstlisting}[language=C++]
sem_t mutex = 1;
sem_t libres = K;
sem_t ocupados = 0;
int productores_activos = p;
bool canal_cerrado = false;
int elementos_en_buffer = 0;

void enviar(T elem) {
    sem_wait(&libres);
    sem_wait(&mutex);
    buffer.push(elem);
    elementos_en_buffer++;
    sem_post(&mutex);
    sem_post(&ocupados);
}

void terminar_productor() {
    sem_wait(&mutex);
    productores_activos--;
    if (productores_activos == 0) {
        canal_cerrado = true;
        // Despertar a posibles consumidores bloqueados
        for (int i = 0; i < q; i++) sem_post(&ocupados);
    }
    sem_post(&mutex);
}

bool recibir(T &elem) {
    sem_wait(&ocupados);
    sem_wait(&mutex);
    if (elementos_en_buffer == 0 && canal_cerrado) {
        // Cascada para liberar a otros consumidores terminados
        sem_post(&ocupados);
        sem_post(&mutex);
        return false; // Senal de fin de canal
    }
    elem = buffer.pop();
    elementos_en_buffer--;
    sem_post(&mutex);
    sem_post(&libres);
    return true;
}
\end{lstlisting}
\end{solucion}

\begin{ejercicio}[50: Asignación Multidimensional de Recursos Todo o Nada]
Tres clases de recursos $(N_A, N_B, N_C)$. Diseñar monitor con reserva atómica, comparar FIFO frente a primera satisfacible y política de envejecimiento.
\end{ejercicio}

\begin{solucion}
\begin{lstlisting}[language=C++]
class MonitorMultirrecurso {
private:
    std::mutex cerrojo;
    std::condition_variable cola;
    int dispA, dispB, dispC;
    int ticket_turno = 0;
    int ticket_siguiente = 0;

public:
    void adquirir_fifo(int a, int b, int c) {
        std::unique_lock<std::mutex> lock(cerrojo);
        int mi_ticket = ticket_siguiente++;
        while (mi_ticket != ticket_turno || dispA < a || dispB < b || dispC < c) {
            cola.wait(lock);
        }
        dispA -= a; dispB -= b; dispC -= c;
        ticket_turno++;
        cola.notify_all();
    }

    void liberar(int a, int b, int c) {
        std::unique_lock<std::mutex> lock(cerrojo);
        dispA += a; dispB += b; dispC += c;
        cola.notify_all();
    }
};
\end{lstlisting}
\textbf{Comparativa de Políticas de Admisión:}
\begin{itemize}
    \item \textbf{Primera satisfacible:} Maximiza el uso del hardware al no bloquear peticiones pequeñas si hay una grande esperando, pero produce \textbf{inanición de procesos con solicitudes grandes}.
    \item \textbf{FIFO estricto:} Garantiza vivacidad y equidad absoluta a costa de reducir el rendimiento global si la cabeza de la cola pide más de lo disponible.
\end{itemize}
\end{solucion}

\begin{ejercicio}[51: Barrera Reutilizable con Bajas Dinámicas y Plazo Vencido]
Barrera para $N \ge 3$ hilos con generaciones numeradas, soporte de bajas y semántica de barrera rota (\emph{broken barrier}).
\end{ejercicio}

\begin{solucion}
Si vence el plazo de espera (\emph{timeout}) de uno de los hilos, se produce la ruptura de la barrera: todos los hilos que esperan en esa misma generación son despertados lanzando una excepción \texttt{BrokenBarrierException}:
\begin{lstlisting}[language=C++]
class BarreraGeneracional {
private:
    std::mutex cerrojo;
    std::condition_variable cola;
    int participantes_activos;
    int esperando = 0;
    int generacion = 0;
    bool rota = false;

public:
    BarreraGeneracional(int n) : participantes_activos(n) {}

    void darse_de_baja() {
        std::unique_lock<std::mutex> lock(cerrojo);
        participantes_activos--;
        if (esperando == participantes_activos) {
            generacion++;
            esperando = 0;
            cola.notify_all();
        }
    }

    void sincronizar(int timeout_ms) {
        std::unique_lock<std::mutex> lock(cerrojo);
        int gen_local = generacion;
        if (rota) throw std::runtime_error("Barrera Rota");

        esperando++;
        if (esperando == participantes_activos) {
            esperando = 0;
            generacion++;
            cola.notify_all();
            return;
        }

        auto status = cola.wait_for(lock, std::chrono::milliseconds(timeout_ms),
            [&] { return generacion != gen_local || rota; });

        if (!status) {
            rota = true;
            cola.notify_all();
            throw std::runtime_error("Timeout: Barrera Rota");
        }
        if (rota) throw std::runtime_error("Barrera Rota por otro hilo");
    }
};
\end{lstlisting}
\end{solucion}

\begin{ejercicio}[53: Transferencias Concurrentes entre Dos Servicios Independientes]
Servicios $A$ y $B$ con saldos no negativos. No se permite monitor global ni retener un monitor esperando en otro.
\end{ejercicio}

\begin{solucion}
\textbf{1. Prevención de Interbloqueo con Orden Parcial de Cierres:}\\
Si una transferencia $A \to B$ adquiere primero el cerrojo de $A$ y luego el de $B$, mientras una transferencia $B \to A$ adquiere primero $B$ y luego $A$, surge interbloqueo.
\textbf{Solución:} Establecer una regla de orden global en memoria (ej. por dirección o identificador alfabético $id_A < id_B$):
\begin{lstlisting}[language=C++]
void transferir(Servicio &origen, Servicio &destino, int cantidad) {
    Servicio &primero = (origen.id < destino.id) ? origen : destino;
    Servicio &segundo = (origen.id < destino.id) ? destino : origen;

    std::unique_lock<std::mutex> lk1(primero.cerrojo);
    std::unique_lock<std::mutex> lk2(segundo.cerrojo);

    if (origen.saldo >= cantidad) {
        origen.saldo -= cantidad;
        destino.saldo += cantidad;
    }
}
\end{lstlisting}
\textbf{Invariante Global de Conservación:} En todo estado se verifica:
\[
\text{Saldo}(A) + \text{Saldo}(B) = \text{Saldo Inicial}(A) + \text{Saldo Inicial}(B)
\]
\textbf{2. Tolerancia a Fallos:} En sistemas distribuidos con caída de nodos, la transferencia debe dividirse en dos fases (Protocolo Two-Phase Commit - 2PC) con un identificador unívoco de transacción y un registro persistente (\emph{write-ahead log}) para deshacer cargos parciales si el nodo receptor colapsa.
\end{solucion}

\begin{ejercicio}[54. Propiedades de corrección]
Considerar las cuatro exigencias habituales del problema de la exclusión mutua: exclusión mutua, progreso o
ausencia de interbloqueo, ausencia de inanición y espera acotada (equidad). Clasificar cada una como propiedad de
seguridad o de vivacidad, precisando las hipótesis necesarias sobre la planificación. Explicar mediante ejemplos
por qué garantizar exclusión mutua y ausencia de interbloqueo no implica necesariamente ausencia de inanición.
¿Qué se puede afirmar de un algoritmo que únicamente satisface las cuatro condiciones de Dijkstra estudiadas en
clase? Explicitar qué formulación de dichas condiciones se utiliza.
\end{ejercicio}
\begin{solucion}
\textbf{1. Clasificación.} Seguridad: «nunca pasa nada malo»; se incumple en un prefijo finito de la traza.
Vivacidad: «algo bueno acabará pasando»; solo se incumple en una ejecución infinita.
\begin{center}\small
\begin{tabular}{p{3.0cm}p{3.0cm}p{7.0cm}}
\toprule
\textbf{Exigencia} & \textbf{Tipo} & \textbf{Hipótesis de planificación} \\ \midrule
Exclusión mutua & seguridad & ninguna: tiene que cumplirse con cualquier intercalación. \\
Ausencia de interbloqueo & seguridad (diap.\ 1.25: «nunca ocurrirá que los procesos se encuentren esperando algo que nunca sucederá») & ninguna para el interbloqueo estático. \\
Progreso & vivacidad & si la SC está libre y hay procesos esperando, alguno acabará entrando. Hace falta
\textbf{progreso finito}: todo proceso que puede ejecutar acaba ejecutando (planificación débilmente justa) y
nadie se queda para siempre en la SC. \\
Ausencia de inanición & vivacidad (individual) & cada proceso que lo pide acaba entrando. Hace falta
planificación débilmente justa y tiempo finito en la SC. \\
Espera acotada (equidad) & vivacidad en la terminología de Capel (diap.\ 1.26: «tipo particular de propiedad de
vivacidad») & cota de \emph{adelantamientos}, no de tiempo. Para acotar el tiempo hay que acotar además las
velocidades relativas. \\
\bottomrule
\end{tabular}
\end{center}
Matiz para justificar: con una cota $K$ explícita, «nadie adelanta más de $K$ veces» se incumple en un prefijo
finito ($K+1$ adelantamientos), así que formalmente es de seguridad. En el test, sigue la clasificación de Capel.

\textbf{2. EM + ausencia de interbloqueo $\not\Rightarrow$ ausencia de inanición.} La ausencia de interbloqueo
es colectiva («alguien entra»); la de inanición, individual («entro yo»).
\begin{itemize}[leftmargin=*]
  \item \emph{Cerrojo con \texttt{swap} y 3 procesos (problema 58).} P1 y P2 se alternan en la SC. El
        planificador ejecuta el \texttt{swap} de P3 solo cuando \texttt{ocupado} es cierto. Siempre hay alguien
        dentro (no hay interbloqueo), nunca hay dos (EM), y P3 da pasos sin entrar jamás: inanición.
  \item \emph{Algoritmo de Dijkstra para $N$} (diap.\ 2.13): dos procesos rápidos se pasan el turno y un tercero
        siempre consulta \texttt{c[turno]} cuando el dueño del turno no está pasivo.
\end{itemize}

\textbf{3. Formulación usada: la de las diapositivas (2.3).}
\begin{enumerate}[leftmargin=*,noitemsep]
  \item No hacer ninguna suposición acerca de las instrucciones o número de procesos soportados por el
        multiprocesador.
  \item Ni tampoco acerca de la velocidad de ejecución de los procesos, excepto que no es cero (progreso finito).
  \item Cuando un proceso se encuentra ejecutando código fuera de la sección crítica no puede impedir a los otros
        procesos entrar en ésta.
  \item La sección crítica siempre será alcanzada por alguno de los procesos que esperan entrar.
\end{enumerate}
Un algoritmo con EM que solo cumple estas cuatro es \textbf{parcialmente correcto}. Es seguro, independiente del
hardware y de las velocidades, y no tiene interbloqueo: la SC es alcanzable y nadie bloquea desde fuera. Pero
\textbf{no garantiza la ausencia de inanición} ni una cota de espera calculable (la 5ª condición, de Knuth). El
ejemplo canónico es el algoritmo de Dijkstra de 1965.

Si se usara la formulación de los libros (EM, progreso y espera limitada), la tercera exigencia ya incluiría la
ausencia de inanición, y la conclusión cambiaría. Por eso el enunciado pide decir cuál se usa.
\end{solucion}

% ---------------------------------------------------------------------- 55
\begin{ejercicio}[55. Dos indicadores sin variable de turno]
Sean dos procesos con las variables compartidas \texttt{b[0]} y \texttt{b[1]}, inicialmente falsas, y el
siguiente protocolo, ejecutado por \texttt{P(i)} (\texttt{j=1-i}):
\begin{lstlisting}
b[i] := true;
while b[j] do
    b[i] := false;
    while b[j] do skip;
    b[i] := true;
endwhile;
<seccion critica>;
b[i] := false;
\end{lstlisting}
Analizar por separado: (a) exclusión mutua; (b) ausencia de interbloqueo; (c) ausencia de inanición. Si alguna
propiedad no se satisface, construir un escenario concreto. Comparar el papel de la variable de turno en este
algoritmo y en el de Peterson para dos procesos.
\end{ejercicio}
\begin{solucion}
\textbf{(a) EM: se cumple.} $P_i$ solo entra tras leer \texttt{b[j] = false} en la guarda externa. Antes de esa
lectura ejecutó su último \texttt{b[i] := true} (línea 1 o 5), y \texttt{b[i]} sigue cierto hasta que sale de la
SC. Supongamos los dos dentro y sean $t_0$ y $t_1$ los instantes de esas últimas lecturas, con $t_0 < t_1$ sin
pérdida de generalidad. En $t_0$, \texttt{b[0]} ya era cierto y lo sigue siendo hasta que P0 sale, después de
$t_1$. Entonces P1 leyó \texttt{b[0] = true} en $t_1$ y no pudo pasar. Contradicción: $N_{SC} \le 1$.

\textbf{(b) Interbloqueo: no hay un estado bloqueado, pero sí livelock.} Desde cualquier estado, otra
planificación deja entrar a alguno. Sin embargo, si los dos van al mismo ritmo, ceden a la vez para siempre:
\begin{center}\small
\begin{tabular}{clcc}
\toprule
\textbf{Paso} & \textbf{Acción (P0 y P1 a la par)} & \texttt{b[0]} & \texttt{b[1]} \\ \midrule
1 & los dos: \texttt{b[i] := true} & T & T \\
2 & los dos evalúan \texttt{while b[j]}: cierto, entran al bucle & T & T \\
3 & los dos: \texttt{b[i] := false} & F & F \\
4 & los dos evalúan \texttt{while b[j] do skip}: falso, salen & F & F \\
5 & los dos: \texttt{b[i] := true} & T & T \\
\bottomrule
\end{tabular}
\end{center}
Se vuelve al estado del paso 2 indefinidamente, con la SC libre y ninguno dentro. \textbf{No se garantiza el
progreso.}

\textbf{(c) Inanición: puede haberla.} P0 espera en \texttt{while b[1] do skip} con \texttt{b[0] = false}. P1 entra
en la SC y sale (\texttt{b[1] := false}), y vuelve enseguida a \texttt{b[1] := true} y a entrar, porque
\texttt{b[0]} es falso. El planificador ejecuta la comprobación de P0 solo cuando \texttt{b[1]} es cierto. P0 da
pasos (la planificación es débilmente justa), pero no entra nunca.

\textbf{Papel del turno.} Aquí \textbf{no hay variable de turno}: la decisión depende solo de dos indicadores
simétricos. Ante un conflicto los dos ven lo mismo y hacen lo mismo («pase usted»), de ahí el livelock. En
Peterson los dos escriben \texttt{turno} y la variable guarda el valor del último, así que exactamente uno de los
dos espera. Eso rompe la simetría y además acota la espera a un adelantamiento.
\end{solucion}

\begin{ejercicio}[56. El algoritmo de Hyman]
Se comparte \texttt{c[0]=c[1]=1} y \texttt{turno=1}. Cada proceso \texttt{P(i)}, con \texttt{j=1-i}, ejecuta:
\begin{lstlisting}
c[i] := 0;
while turno != i do
    while c[j] = 0 do skip;
    turno := i;
endwhile;
<seccion critica>;
c[i] := 1;
\end{lstlisting}
Determinar si el algoritmo garantiza exclusión mutua. Si no la garantiza, proporcionar una intercalación de
instrucciones que lleve simultáneamente a ambos procesos a sus secciones críticas. Identificar exactamente la
decisión de diseño que permite el fallo.
\end{ejercicio}
\begin{solucion}
\textbf{No garantiza la EM.} Contraejemplo:
\begin{center}\small
\begin{tabular}{clllc}
\toprule
\textbf{Paso} & \textbf{Proc.} & \textbf{Instrucción} & \textbf{c[0] c[1] turno} & \textbf{Comentario} \\ \midrule
1 & P0 & \texttt{c[0] := 0} & 0 \; 1 \; 1 & \\
2 & P0 & \texttt{turno != 0}: cierto & 0 \; 1 \; 1 & entra al bucle \\
3 & P0 & \texttt{c[1] = 0}: falso & 0 \; 1 \; 1 & no espera \\
-- & & \multicolumn{3}{l}{\emph{el planificador suspende a P0 antes de \texttt{turno := 0}}} \\
4 & P1 & \texttt{c[1] := 0} & 0 \; 0 \; 1 & \\
5 & P1 & \texttt{turno != 1}: falso & 0 \; 0 \; 1 & \textbf{P1 entra en la SC} \\
6 & P0 & \texttt{turno := 0} & 0 \; 0 \; 0 & \\
7 & P0 & \texttt{turno != 0}: falso & 0 \; 0 \; 0 & \textbf{P0 entra en la SC} \\
\bottomrule
\end{tabular}
\end{center}
Estado final: P0 y P1 en la SC. \textbf{Se viola la EM.}

\textbf{Decisión de diseño que falla.} Comprobar la clave del otro (\texttt{c[j] = 0}) y apropiarse del turno
(\texttt{turno := i}) son dos pasos separados, y después de tomar el turno \emph{no se vuelve a comprobar}
\texttt{c[j]}. Además, el que ya tiene el turno entra sin mirar la clave del otro. Dekker evita las dos cosas:
solo entra quien ve la clave del otro a 1, y el turno solo decide quién cede.
\end{solucion}

\begin{ejercicio}[57. Peterson para dos procesos]
Sean \texttt{quiere[0]=quiere[1]=false} y \texttt{turno} compartido. Cada \texttt{P(i)} ejecuta:
\begin{lstlisting}
quiere[i] := true;
turno := 1-i;
while quiere[1-i] and turno = 1-i do skip;
<seccion critica>;
quiere[i] := false;
\end{lstlisting}
(a) Demostrar la exclusión mutua. (b) Argumentar el progreso y la ausencia de inanición, indicando las hipótesis
de planificación. (c) Investigar qué sucede si se intercambia el orden de las dos primeras asignaciones. (d)
Explicar por qué la corrección en un modelo secuencialmente consistente no autoriza a usar sin más variables
ordinarias en un programa real con memoria débil.
\end{ejercicio}
\begin{solucion}
\textbf{(a) EM.} Supongamos P0 y P1 a la vez en la SC. Ninguno ha ejecutado la salida, así que
\texttt{quiere[0] = quiere[1] = true}. Sea $P_k$ el último que escribió \texttt{turno} (escribió
\texttt{turno := 1-k}). Nadie lo cambia después mientras los dos siguen dentro. Cuando $P_k$ evaluó su guarda tras
esa escritura, \texttt{turno = 1-k} y \texttt{quiere[1-k] = true}: el otro lo puso a cierto antes de escribir
\texttt{turno}, y por tanto antes que $P_k$. La guarda era cierta y $P_k$ no pudo salir del bucle.
Contradicción: $N_{SC} \le 1$.

\textbf{(b) Progreso.} Si solo $P_i$ quiere entrar, \texttt{quiere[1-i]} es falso y entra sin esperar (no hay
alternancia forzosa). Si quieren los dos, para que esperen ambos haría falta \texttt{turno = 1} y
\texttt{turno = 0} a la vez, lo cual es imposible: uno pasa. Hipótesis: progreso finito, es decir, el que puede
avanzar acaba ejecutando.

\textbf{Sin inanición.} $P_i$ espera con \texttt{quiere[j] and turno = j}. Suponemos que $P_j$ sale de la SC en
tiempo finito y que la planificación es débilmente justa. Al salir, $P_j$ pone \texttt{quiere[j] := false}. Si
vuelve a pedir, escribe \texttt{turno := i}; desde ese momento la guarda de $P_i$ es falsa y \emph{sigue siéndolo},
porque solo $P_i$ podría volver a poner \texttt{turno := j}. Así que $P_i$ entra. \textbf{Espera acotada: a lo sumo
un adelantamiento}, y no depende de las velocidades: aunque $P_i$ sea lentísimo, $P_j$ no puede entrar dos veces
seguidas mientras $P_i$ espera (comprobado con el verificador).

\textbf{(c) Intercambiar \texttt{quiere[i] := true} y \texttt{turno := 1-i} rompe la EM:}
\begin{enumerate}[leftmargin=*,noitemsep]
  \item P0: \texttt{turno := 1}.
  \item P1: \texttt{turno := 0}; \texttt{quiere[1] := true}.
  \item P1 evalúa la guarda: \texttt{quiere[0]} es falso, así que \textbf{P1 entra}.
  \item P0: \texttt{quiere[0] := true}. Evalúa la guarda: \texttt{turno = 0}, que es distinto de 1, así que la
        guarda es falsa y \textbf{P0 entra}.
\end{enumerate}
El orden importa porque, en el original, quien escribe el turno el último ya ha publicado su indicador, y el otro
lo verá. Con el orden cambiado, P1 escribe el turno el último antes de que P0 haya publicado nada.

\textbf{(d) Memoria débil.} La demostración supone \textbf{consistencia secuencial}: todos ven las operaciones en un
único orden que respeta el orden de cada programa. Los procesadores reales tienen \emph{store buffers} y permiten
adelantar una lectura a una escritura anterior (reordenación \emph{store-load}), y el compilador también puede
reordenar o guardar en registros las variables ordinarias. Así, $P_i$ puede leer \texttt{quiere[j] = false} antes de
que su propio \texttt{quiere[i] := true} sea visible para el otro. Si los dos lo hacen, entran a la vez. Hay que usar
variables atómicas con orden secuencialmente consistente (\texttt{std::atomic} con \texttt{seq\_cst}) o barreras
de memoria (\texttt{mfence}, \texttt{dmb}).
\end{solucion}

\begin{ejercicio}[58. Instrucción atómica swap]
Se dispone de \texttt{swap(x,y)}, que intercambia atómicamente los valores booleanos de \texttt{x} e \texttt{y}.
Diseñar protocolos de entrada y salida para $N \ge 2$ procesos mediante una variable compartida \texttt{ocupado},
inicialmente falsa, y una variable booleana local por proceso. Demostrar la exclusión mutua y discutir el
progreso, la inanición y el coste de espera ocupada. ¿Basta la atomicidad de \texttt{swap} para asegurar equidad?
Justificar.
\end{ejercicio}
\begin{solucion}
\begin{lstlisting}
-- compartida: ocupado := false ;   local de Pi: llave
llave := true;
repeat
    swap(ocupado, llave);
until llave = false;
<seccion critica>;
ocupado := false;
\end{lstlisting}
\textbf{EM.} Sea $D$ el número de procesos que han obtenido \texttt{llave = false} y aún no han ejecutado
\texttt{ocupado := false} (los que están en la SC). Invariante:
\[
D + [\,\texttt{ocupado} = \text{false}\,] = 1 \qquad ([\cdot] \text{ vale 1 si es cierto y 0 si no}).
\]
Al principio $D = 0$ y \texttt{ocupado} es falso: $0 + 1 = 1$. Hay tres casos:
\begin{itemize}[leftmargin=*,noitemsep]
  \item Un \texttt{swap} con \texttt{ocupado} falso: ese proceso recibe falso ($D$ aumenta en 1) y
        \texttt{ocupado} pasa a cierto (el corchete pasa de 1 a 0). La suma sigue en 1.
  \item Un \texttt{swap} con \texttt{ocupado} cierto: el proceso recibe cierto y no cambia nada.
  \item La salida: $D$ disminuye en 1 y \texttt{ocupado} vuelve a falso.
\end{itemize}
Por tanto $D \le 1$, es decir, $N_{SC} \le 1$.

\textbf{Progreso.} Si la SC está libre, \texttt{ocupado} es falso y el primer \texttt{swap} que se ejecute lo toma:
no hay interbloqueo.

\textbf{Inanición: puede haberla.} Cuando la SC se libera, gana quien ejecute antes su \texttt{swap}. Con 3 procesos,
P1 y P2 se alternan y el \texttt{swap} de P3 siempre llega con \texttt{ocupado} cierto.

\textbf{¿Basta la atomicidad para la equidad? No.} La atomicidad garantiza que cada intercambio es indivisible,
pero no dice nada sobre \emph{qué} proceso gana la siguiente carrera: no hay cola ni turno. Para tener equidad hace
falta un orden explícito, por ejemplo tickets o una cola.

\textbf{Coste de la espera ocupada.} El proceso que espera consume CPU sin hacer trabajo útil, y en un
monoprocesador gasta su quantum mientras el dueño no puede avanzar. Además, cada \texttt{swap} es una escritura que
invalida la línea de caché en los demás núcleos (tráfico de coherencia). Se mitiga con
\emph{test-and-test-and-set}: esperar leyendo \texttt{while ocupado do skip} y solo intentar el \texttt{swap}
cuando se lea falso.
\end{solucion}

\begin{ejercicio}[59. Exclusión de capacidad k]
Un recurso admite simultáneamente a lo sumo $k$ procesos, con $1 \le k < N$. Diseñar las subrutinas
\texttt{entrar()} y \texttt{salir()} para $N$ procesos utilizando únicamente una variable entera compartida
\texttt{dentro}, inicialmente cero, y un cerrojo atómico \texttt{lock()} / \texttt{unlock()}. Se permite espera
ocupada fuera del cerrojo. (a) Escribir pseudocódigo. (b) Demostrar el invariante $0 \le \texttt{dentro} \le k$.
(c) Explicar por qué no debe mantenerse el cerrojo mientras se espera a que haya capacidad. (d) Discutir si la
solución asegura ausencia de inanición.
\end{ejercicio}
\begin{solucion}
\textbf{(a)}
\begin{lstlisting}
entrar():  ok := false;
           repeat
             lock();
             if dentro < k then begin dentro := dentro + 1; ok := true; end;
             unlock();
             -- si no habia plaza, la espera sigue FUERA del cerrojo
           until ok;

salir():   lock(); dentro := dentro - 1; unlock();
\end{lstlisting}
\textbf{(b) Invariante.} \texttt{dentro} es el número de procesos que han completado \texttt{entrar()} y no han
completado \texttt{salir()}, y cumple $0 \le \texttt{dentro} \le k$. Solo se modifica con el cerrojo cogido, así
que cada lectura-modificación-escritura es indivisible. Al principio vale $0$.
\begin{itemize}[leftmargin=*,noitemsep]
  \item \textbf{Incremento}: solo se hace después de comprobar $\texttt{dentro} < k$ con el mismo cerrojo, así que
        tras incrementar vale como mucho $k$.
  \item \textbf{Decremento}: solo lo ejecuta un proceso que está dentro, así que antes vale al menos 1 y después
        al menos 0.
\end{itemize}

\textbf{(c)} Si se esperase con el cerrojo cogido (\texttt{lock(); while dentro >= k do skip;}), ningún proceso de
dentro podría ejecutar \texttt{salir()}, porque necesita ese cerrojo. \texttt{dentro} no bajaría nunca: hay
\textbf{interbloqueo}, y además el que espera impide entrar también a todos los demás.

\textbf{(d) No asegura la ausencia de inanición.} Cuando se libera una plaza, la gana quien coja antes el
cerrojo. Un proceso puede llegar tarde siempre: incluso con un cerrojo FIFO, entre su \texttt{unlock()} y su
siguiente \texttt{lock()} otro puede ocupar la plaza. Para evitarlo hace falta un orden de llegada (tickets o
cola).
\end{solucion}

\begin{ejercicio}[60. Algoritmo de turnos circulares]
Para $N \ge 2$ procesos se comparte \texttt{s[0..N-1]}, inicialmente a cero. El proceso $P_i$ espera hasta que se
cumpla \texttt{s[i] != s[i-1]} si $i > 0$, o \texttt{s[0] = s[N-1]} si $i = 0$. Al salir, ejecuta
\texttt{s[i]:=s[i-1]} si $i > 0$, o \texttt{s[0]:=1-s[0]} si $i = 0$. (a) Examinar la exclusión mutua. (b) ¿Qué
sucede si un proceso permanece indefinidamente en su sección no crítica? (c) Determinar si se cumple el
requisito de progreso cuando solamente un proceso desea entrar. (d) Distinguir entre alternancia forzosa y
equidad entre procesos contendientes.
\end{ejercicio}
\begin{solucion}
\textbf{(a) EM: se cumple.} Diremos que $P_i$ está \emph{habilitado} si se cumple su condición de entrada. Los
estados alcanzables del vector son de dos formas:
\begin{itemize}[leftmargin=*,noitemsep]
  \item todo igual, $(v,\dots,v)$: solo está habilitado $P_0$;
  \item $(v,\dots,v,\,1-v,\dots,1-v)$ con el cambio en la posición $k$ ($1 \le k \le N-1$): solo está habilitado
        $P_k$.
\end{itemize}
En cualquier estado hay \textbf{exactamente un} proceso habilitado. Solo escribe en \texttt{s} el que sale de la
SC, que es el habilitado, y al salir pasa la habilitación a su sucesor:
\begin{itemize}[leftmargin=*,noitemsep]
  \item $P_0$ invierte \texttt{s[0]} y habilita a $P_1$;
  \item $P_k$ copia \texttt{s[k-1]}, desplaza el cambio una posición y habilita a $P_{k+1}$; el último devuelve el
        vector a «todo igual» y habilita a $P_0$.
\end{itemize}
Funciona como un \textbf{testigo implícito} que da la vuelta al anillo. Como nunca hay dos habilitados,
$N_{SC} \le 1$.

\textbf{(b)} Si el proceso que tiene el testigo se queda en su SNC, no sale nunca de la SC (no la usa) y no pasa el
testigo: \textbf{nadie más vuelve a entrar}. Si no lo tiene, en cuanto el testigo le llegue el sistema se detiene
igual. Se viola la \textbf{3ª condición de Dijkstra}: un proceso fuera de la SC impide entrar a los demás.

\textbf{(c) No se cumple el progreso.} Si solo $P_3$ quiere entrar y el testigo lo tiene $P_0$, que no quiere, $P_3$
espera para siempre con la SC libre.

\textbf{(d)} \emph{Alternancia forzosa}: el orden $P_0, P_1, \dots, P_{N-1}$ está fijado de antemano y cada uno tiene
que usar su turno para pasarlo, quiera o no la SC. Es lo que rompe el progreso. \emph{Equidad}: solo se refiere a
los procesos que \emph{compiten}: ninguno es adelantado indefinidamente (o más de $K$ veces), pero se puede saltar a
los que no quieren entrar. El anillo acota la espera a $N-1$ entradas, pero no es aceptable porque incumple el
progreso. Por eso la equidad no basta: hay que exigir también la 3ª condición.
\end{solucion}

\begin{ejercicio}[61. Tickets para dos procesos]
Se comparten \texttt{n[0]=n[1]=0}. Cada \texttt{P(i)}, con \texttt{j=1-i}, ejecuta:
\begin{lstlisting}
n[i] := 1;
n[i] := n[j] + 1;
while n[j] != 0 and
      (n[j] < n[i] or (n[j] = n[i] and j < i)) do
    skip;
endwhile;
<seccion critica>;
n[i] := 0;
\end{lstlisting}
(a) Estudiar la exclusión mutua, considerando todas las intercalaciones relevantes de las asignaciones iniciales.
(b) Analizar si el protocolo puede producir interbloqueo o inanición. (c) Estudiar qué ocurre al eliminar la
asignación \texttt{n[i]:=1}. (d) Explicar la función del desempate por identificador. No suponer que la lectura de
\texttt{n[j]} y la escritura posterior constituyen una operación indivisible.
\end{ejercicio}
\begin{solucion}
$P_i$ espera mientras $P_j$ tiene un ticket y el par $(n[j], j)$ es menor que $(n[i], i)$ en orden lexicográfico.
Para cada proceso distinguimos cuatro pasos:
\begin{itemize}[leftmargin=*,noitemsep]
  \item $d_i$: la escritura \texttt{n[i]:=1} (la \emph{puerta});
  \item $r_i$: la lectura de \texttt{n[j]};
  \item $w_i$: la escritura del ticket $T_i = \text{(valor leído)} + 1$;
  \item $e_i$: la última evaluación de la guarda, la que deja pasar.
\end{itemize}

\textbf{(a) EM: se cumple.} Sea $P_i$ el primero en entrar ($e_i$) y supongamos que $P_j$ entra mientras $P_i$
sigue dentro. Mientras $P_i$ está en la SC, \texttt{n[i]} vale $T_i \ge 1$. Basta ver que $(T_i, i) < (T_j, j)$,
porque entonces la guarda de $P_j$ es cierta y no puede pasar. Casos según cuándo lee $P_j$ (\,$r_j$\,):
\begin{center}\small
\begin{tabular}{p{3.6cm}p{10.2cm}}
\toprule
\textbf{Caso} & \textbf{Razonamiento} \\ \midrule
$r_j$ después de $w_i$ & $P_j$ lee $T_i$, así que $T_j = T_i + 1 > T_i$: $P_j$ espera. \\
$r_j$ antes de $d_i$ & $P_j$ lee 0, así que $T_j = 1$. Pero entonces $r_i > d_i > r_j > d_j$ y $P_i$ lee
\texttt{n[j]} $= 1$, así que $T_i = 2$. En $e_i$, $P_j$ sigue en su entrada con \texttt{n[j]} $= 1 < 2$: $P_i$ no
habría podido pasar. \textbf{Caso imposible.} \\
$r_j$ entre $d_i$ y $w_i$ & $P_j$ lee 1, así que $T_j = 2$. Si $P_i$ leyó antes de $d_j$, $T_i = 1 < 2$: $P_j$
espera. Si no, $T_i \in \{2, 3\}$. Con $T_i = 3$, o con \texttt{n[j]} $= 1$ en $e_i$, $P_i$ no habría pasado
(imposible). Solo queda $T_i = T_j = 2$, que se desempata por identificador: si $P_i$ pasó, es que $i < j$, y
entonces $P_j$ espera. \\
\bottomrule
\end{tabular}
\end{center}
En todos los casos $P_j$ no puede entrar mientras $P_i$ está dentro: $N_{SC} \le 1$. El verificador lo confirma en
todas las intercalaciones.

\textbf{(b) Interbloqueo: no.} Para que esperen los dos harían falta los dos tickets distintos de 0 y que cada par
fuese menor que el otro, lo cual es imposible porque el orden lexicográfico es total.

\textbf{Inanición: no, y la espera está acotada a un adelantamiento.} Supongamos que $P_i$ espera con ticket $T$ y
que $P_j$, en la SC, sale en tiempo finito. Al salir pone \texttt{n[j]} $:= 0$. Si vuelve a pedir, lee
\texttt{n[i]} $= T$ y toma $T + 1$, de modo que desde $w_j$ la guarda de $P_i$ es falsa de forma estable. Aunque
$P_i$ sea muy lento, $P_j$ no le adelanta dos veces (comprobado). Un detalle: si se solapan siempre, los tickets
crecen sin límite.

\textbf{(c) Sin \texttt{n[i]:=1} se pierde la EM:}
\begin{enumerate}[leftmargin=*,noitemsep]
  \item P0 lee \texttt{n[1]} $= 0$ y se suspende antes de escribir su ticket.
  \item P1 lee \texttt{n[0]} $= 0$ y escribe \texttt{n[1]} $:= 1$. En su guarda, \texttt{n[0]} $= 0$, así que
        \textbf{P1 entra}.
  \item P0 escribe \texttt{n[0]} $:= 0 + 1 = 1$. En su guarda hay empate (1, 1) y $j = 1$ no es menor que $i = 0$,
        así que la guarda es falsa y \textbf{P0 entra}.
\end{enumerate}
La puerta \texttt{n[i]:=1} avisa de que $P_i$ \emph{está calculando} su ticket. Sin ella, el otro lo cree inactivo
porque ve \texttt{n[i]} $= 0$.

\textbf{(d) Desempate por identificador.} La lectura y la escritura no son indivisibles, así que los dos pueden
leer el 1 de la puerta del otro y obtener el mismo ticket (2 y 2). Si la guarda solo comparase con $<$, los dos
pasarían (se pierde la EM); si comparase con $\le$, los dos esperarían (interbloqueo). Con el par (ticket, id) el
orden es total y siempre decide uno.
\end{solucion}

\begin{ejercicio}[62. Peterson para N procesos: filtro por niveles]
Considerar la generalización de Peterson con \texttt{nivel[i]} inicialmente cero y \texttt{victima[L]}
compartidos. Cada proceso $P_i$ recorre los niveles $L = 1, \dots, N-1$:
\begin{lstlisting}
for L := 1 to N-1 do
    nivel[i] := L;
    victima[L] := i;
    while exists j != i such that
          nivel[j] >= L and victima[L] = i do skip;
endfor;
<seccion critica>;
nivel[i] := 0;
\end{lstlisting}
(a) Justificar por qué no pueden coexistir dos procesos en sección crítica. (b) Analizar si pueden encontrarse dos
procesos en el nivel $N-2$ mientras ninguno está en $N-3$; razonar según la definición precisa de «estar en un
nivel». (c) Examinar qué hipótesis adicionales serían necesarias para establecer cotas de espera. Evitar
identificar automáticamente ausencia de inanición con espera acotada.
\end{ejercicio}
\begin{solucion}
Es el algoritmo de las diapositivas con otros nombres: \texttt{nivel} es \texttt{c}, \texttt{victima} es
\texttt{turno}, y los niveles $1..N-1$ son las etapas $0..N-2$. Dos observaciones que se usan en todo el
razonamiento:
\begin{itemize}[leftmargin=*,noitemsep]
  \item \texttt{nivel[i]} no baja hasta que $P_i$ sale de la SC;
  \item $P_i$ escribe \texttt{nivel[i]} antes que \texttt{victima[L]}.
\end{itemize}

\textbf{(a) Lema: en cada momento, a lo sumo $N - L$ procesos han superado el nivel $L$.} Superar un nivel es salir
de su \texttt{while}. Se demuestra por inducción sobre $L$; para $L = 0$ es trivial.

Supongamos que hay un conjunto $S$ de $N - L + 1 \ge 2$ procesos que han superado $L$, y sea $A$ el último de $S$
en escribir \texttt{victima[L]}.
\begin{itemize}[leftmargin=*,noitemsep]
  \item \emph{Nadie escribe \texttt{victima[L]} después de $A$.} Si lo hiciera un $C$ fuera de $S$, $C$ habría
        superado $L-1$ y seguiría en el nivel $L$, y entonces habría $N-L+2$ procesos por encima de $L-1$, en
        contra de la hipótesis de inducción.
  \item Por tanto, cuando $A$ evaluó su guarda, \texttt{victima[L]} $= A$.
  \item Cualquier $B \in S$ distinto de $A$ escribió \texttt{nivel[B]} $:= L$ antes de escribir
        \texttt{victima[L]}, y por tanto antes que $A$, y sigue con \texttt{nivel[B]} $\ge L$. Así que $A$ leyó
        \texttt{nivel[B]} $\ge L$ y no pudo salir. Contradicción.
\end{itemize}
Para entrar en la SC hay que superar el nivel $N-1$: \textbf{a lo sumo $N - (N-1) = 1$ proceso}. Es el L4 de las
diapositivas («en la etapa $j$ hay como máximo $n - j$»).

\textbf{(b) Definición precisa: $P_i$ está en el nivel $L$ si \texttt{nivel[i]} $= L$.} Es decir, ha escrito $L$ y
todavía no ha escrito $L + 1$, ya esté esperando o ya haya pasado la guarda. La pregunta solo tiene sentido para
$N \ge 4$: con $N = 3$, el «nivel» $N - 3 = 0$ significa «no compite».

\textbf{Respuesta: no puede ocurrir} (es el L3 de las diapositivas). Supongamos $A$ y $B$ en el nivel $N - 2$:
los dos han superado $N - 3$ y tienen \texttt{nivel} $\ge N-3$ desde antes de sus escrituras en
\texttt{victima[N-3]}. Sea $Z$ el último que escribió \texttt{victima[N-3]}.
\begin{itemize}[leftmargin=*,noitemsep]
  \item Si $Z$ fuese $A$ (o $B$), al evaluar su guarda habría visto \texttt{victima[N-3]} $= Z$ y al otro con
        nivel $\ge N - 3$, y no habría podido pasar. Contradicción.
  \item Si $Z$ es un tercer proceso, por la misma razón no ha podido superar $N - 3$, y tampoco ha podido salir
        (para salir hay que pasar todos los niveles). Así que $Z$ sigue con \texttt{nivel[Z]} $= N - 3$.
\end{itemize}
Siempre hay alguien en $N-3$. El verificador lo confirma para $N = 4$: ningún estado alcanzable tiene dos procesos
en el nivel 2 y ninguno en el 1.

\textbf{(c) Inanición frente a espera acotada.}
\begin{itemize}[leftmargin=*]
  \item \textbf{Ausencia de inanición: sí}, con planificación débilmente justa y SC de duración finita. Un proceso
        detenido en el nivel $L$ queda libre en cuanto otro escribe \texttt{victima[L]}, y eso es estable porque
        nadie le devuelve el papel de víctima. Si nadie llega, queda libre cuando los de niveles superiores
        terminan, lo que se razona por inducción desde el nivel más alto.
  \item \textbf{Espera acotada: no se obtiene sin más hipótesis.} Si un proceso es muy lento, por ejemplo uno que
        ya ha sido liberado pero aún no ha ejecutado su siguiente instrucción, otros dos pueden alternarse en la
        SC tantas veces como se quiera; basta con no darle la CPU entretanto. La planificación débilmente justa
        garantiza que acabará ejecutando, pero no \emph{cuándo}. El verificador encuentra ese ciclo para $N = 3$
        y $N = 4$, y en cambio no lo encuentra en Peterson para 2 ni en los tickets del problema 61.
  \item \textbf{Hipótesis para acotar}:
        \begin{itemize}[leftmargin=*,noitemsep]
          \item número finito de procesos;
          \item tiempo finito en la SC;
          \item medir la espera en \textbf{turnos}, entendiendo que en cada turno todo proceso activo da al menos un
                paso; es decir, acotar las velocidades relativas.
        \end{itemize}
        Con ellas se obtiene la cota de las diapositivas: $r(n) = n - 1 + r(n-1) = n(n-1)/2$ turnos.
\end{itemize}
\end{solucion}

\begin{ejercicio}[63. Algoritmo de Dijkstra para N procesos: modificación de una guarda]
Se comparte \texttt{turno} y el vector \texttt{estado[i]} con valores \texttt{pasivo}, \texttt{solicitando} y
\texttt{enSC}. En el algoritmo de Dijkstra estudiado en clase, durante el protocolo de entrada, un proceso que
espera su turno ejecuta:
\begin{lstlisting}
while turno != i do
    if estado[turno] = pasivo then turno := i;
endwhile;
\end{lstlisting}
Se propone sustituir la guarda por \texttt{estado[turno] != enSC}, sin alterar el resto del algoritmo. (a) Comparar
las dos condiciones. (b) Construir, si es posible, una ejecución que invalide alguna propiedad de corrección. (c)
Precisar si el defecto afecta a la seguridad, al progreso o a la equidad. Para el análisis, utilizar el protocolo
completo de Dijkstra presentado en clase, no únicamente el fragmento anterior.
\end{ejercicio}
\begin{solucion}
Protocolo completo (diapositiva 2.11), con la guarda nueva marcada:
\begin{lstlisting}
repeat
  estado[i] := solicitando;
  while turno != i do
    -- original: if estado[turno] = pasivo then ...
    if estado[turno] != enSC then turno := i;
  endwhile;
  estado[i] := enSC;
  j := 0;
  while (j < n) and (j = i or estado[j] != enSC) do j := j+1;
until j >= n;
<seccion critica>;
estado[i] := pasivo;
\end{lstlisting}
\textbf{(a) Comparación.} Con la original, $P_i$ solo toma el turno si su dueño está \texttt{pasivo}, es decir, si
no quiere entrar. Con la nueva, también se lo quita a un dueño que está \texttt{solicitando}. Se respeta solo al que
ya ha llegado a \texttt{enSC}. El argumento de la diapositiva («si un grupo se ve obligado a ciclar, el que posee el
turno no puede estar pasivo, y él pasará») deja de valer, porque ahora se le puede quitar el turno.

\textbf{(b) Ejecución que invalida el progreso} (dos procesos; con tres pasa lo mismo). Al principio los dos están
\texttt{pasivo} y \texttt{turno} $= 0$:
\begin{center}\footnotesize\setlength{\tabcolsep}{3pt}
\begin{tabular}{cllccc}
\toprule
\textbf{Paso} & \textbf{Proc.} & \textbf{Acción} & \texttt{est[0]} & \texttt{est[1]} & \texttt{turno} \\ \midrule
1 & P0 & \texttt{estado[0] := solicitando} & sol & pas & 0 \\
2 & P1 & \texttt{estado[1] := solicitando} & sol & sol & 0 \\
3 & P1 & \texttt{turno != 1} cierto; \texttt{estado[0] != enSC} cierto & sol & sol & 0 \\
4 & P1 & \texttt{turno := 1} & sol & sol & 1 \\
5 & P0 & \texttt{turno != 0} cierto; \texttt{estado[1] != enSC} cierto & sol & sol & 1 \\
6 & P0 & \texttt{turno := 0} & sol & sol & 0 \\
7 & P1 & \texttt{turno != 1} cierto; \texttt{estado[0] != enSC}; \texttt{turno := 1} & sol & sol & 1 \\
8 & P0 & \texttt{turno != 0} cierto; \texttt{estado[1] != enSC}; \texttt{turno := 0} & sol & sol & 0 \\
\bottomrule
\end{tabular}
\end{center}
Los pasos 7 y 8 se repiten para siempre. Los dos dan pasos, lo que es compatible con una planificación débilmente
justa, y ninguno llega a \texttt{enSC} con la SC libre: \textbf{livelock}. Con la guarda original, en el paso 3 P1
habría visto a P0 \texttt{solicitando} y no le habría quitado el turno, y P0 habría pasado.

Hay otro fallo posible: quitarle el turno a uno que ya ha salido del primer bucle pero aún no ha escrito
\texttt{enSC}. Los dos llegan a la segunda barrera, se ven y vuelven a empezar, y eso también puede repetirse.

\textbf{(c) Qué propiedad se pierde.}
\begin{itemize}[leftmargin=*]
  \item \textbf{Seguridad (EM): no se ve afectada.} La garantiza la 2ª barrera, que no cambia. Si $P_i$ y $P_j$
        estuvieran dentro, cada uno habría escrito \texttt{enSC} y \emph{después} habría leído al otro distinto de
        \texttt{enSC}. El que escribió antes lo habría visto en la lectura del otro, así que es imposible. El
        verificador lo confirma con 2 y 3 procesos.
  \item \textbf{Progreso: se pierde.} Hay ejecuciones con la SC libre y procesos esperando en las que nadie entra
        nunca.
  \item \textbf{Equidad}: ya no la tenía (Dijkstra admite inanición), y empeora: ahora pueden quedarse sin entrar
        todos.
\end{itemize}
\end{solucion}
